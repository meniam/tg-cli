# Протокол git и worktree для wrap-up

Всё здесь про то, чтобы оставить репозиторий в состоянии, где ничего не потеряно
и ничего не двусмысленно. Не коммитить, не пушить, не мержить, не удалять и не сносить
без согласия пользователя, если он не дал его раньше в этом же разговоре.

## Рабочее дерево

- `git status` чистый, либо каждое оставшееся изменение намеренное и перечислено
  в отчёте с причиной («оставлено без stage: локальный отладочный конфиг, не для
  коммита»).
- Неотслеживаемые файлы закоммичены, заигнорены или удалены. «Непонятных» нет.
- Изменения только пробелов и форматирования, сделанные инструментом, откачены, если
  форматтер проекта их не требует.
- Не перевернулись переводы строк и режимы файлов (признак: `git diff --stat`
  показывает изменение целых файлов, которые не трогали).

## Коммиты

- Коммиты атомарные: одно намерение на коммит. Смешанную работу разделить до
  завершения (`git add -p` или reset и повторный stage).
- Сообщения по конвенции проекта. Использовать скилл `git-commit`, если доступен:
  он сначала читает конвенции репозитория.
- На ветке для ревью не остаётся fixup- и WIP-коммитов. Squash или reword до push,
  если проект ждёт чистую историю и ветка ещё не общая.
- Ни один коммит не содержит секрет, даже тот, который следующий коммит убрал. Если
  случилось, историю переписать до push, а секрет ротировать в любом случае.
- Футеры сообщений по правилам пользователя. В этом окружении: никаких
  сгенерированных подписей, co-author трейлеров, эмодзи.

## Ветка и remote

- Имя ветки по шаблону проекта.
- Запушена, если работа предназначена для общего доступа, с установленным upstream.
  Не запушена, если пользователь сказал, что работа локальная или экспериментальная;
  в отчёте написать какой случай.
- Отстала от базовой ветки? Rebase или merge по привычке проекта, затем повторный
  прогон гейтов. Не оставлять ветку, которая законфликтует при первом обновлении PR.
- PR или MR: существует, описание совпадает с финальным diff, есть план проверки,
  ссылка на issue. Либо явно отложен с причиной. Ссылку в отчёт.
- Draft PR отмечен как draft, если не готов к ревью.

## Stash

- Stash, созданные по ходу работы, применены или удалены. Тот, что должен остаться,
  получает сообщение (`git stash push -m "..."`) и строку в отчёте.
- Проверять `git stash list`, даже если не помнишь, что создавал: stash от быстрого
  «дай посмотрю на main» легко забыть.

## Локальные ветки

- Брошенные экспериментальные ветки удалены (`git branch -d` удаляет только
  смерженные; `-D` требует причины в отчёте).
- Ветки, чей PR смержен, удалены локально и, если remote не удаляет автоматически,
  на remote тоже.
- Вывод `git branch --no-merged` понятен: у каждой ветки либо есть назначение, либо
  она уходит.

## Выход из worktree

Worktree — отдельный checkout того же репозитория. Сделанная там работа в безопасности
только когда её коммиты достижимы откуда-то надёжного.

1. Внутри worktree: рабочее дерево чистое или намеренные остатки перечислены.
   `git status` и `git stash list` выполнять там, а не в основном checkout.
2. Коммиты достижимы: запушены на remote, или смержены в целевую ветку, или
   пользователь явно хочет оставить ветку локально. Проверить
   `git log <target>..<worktree-branch>`; непустой вывод означает несмерженные коммиты.
3. Выйти из worktree. Если его создавал harness (например, `EnterWorktree` в Claude
   Code), выходить парным инструментом (`ExitWorktree`), чтобы harness обновил своё
   состояние. Иначе `cd` обратно в основной checkout.
4. Удалить: `git worktree remove <path>`. Git откажется, если дерево грязное; этот
   отказ — информация, не добавлять `--force`, чтобы его заглушить.
5. Ветку удалить только если смержена: `git branch -d <branch>`. Если не смержена,
   а пользователь всё равно хочет удалить, `-D` с причиной в отчёте.
6. `git worktree prune`, чтобы убрать устаревшие служебные записи.
7. Проверить `git worktree list`: остались только ожидаемые деревья.

Никогда не удалять worktree или ветку с несмерженными коммитами по своему решению.
Доложить ветку, число коммитов и команду, которую пользователь мог бы выполнить.

## Работа в нескольких репозиториях

Когда задача затронула несколько репозиториев (библиотека и её потребитель,
репозиторий скиллов и проект), пройти чеклист в каждом. В отчёте указать порядок
между репозиториями: что нужно выпустить или смержить первым.

## Строки отчёта

В разделе «Git» отчёта по одной строке на каждое:

- ветка и база
- коммиты (число, или «нет: вся работа в одном существующем коммите»)
- push и PR со ссылкой, или «только локально, по просьбе»
- worktree: удалён, оставлен (почему) или «не использовался»
- stash: нет, или названные оставленные
- локальные ветки подчищены, или перечислены оставшиеся
