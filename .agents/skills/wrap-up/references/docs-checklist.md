# Чеклист документации и памяти для wrap-up

Проверка для каждого документа: говорит ли он правду после этого изменения? Обновлять
те, что перестали. Не дописывать текст в документы, которые никогда не были про эту
область, только чтобы оставить след: история git уже фиксирует изменение.

## Документация проекта

- README и quickstart: шаги установки, требования, команды, порты, список
  возможностей, скриншоты, которые теперь выглядят иначе.
- Справочник конфигурации: новые или переименованные env-переменные, флаги, ключи
  конфига, значения по умолчанию. `.env.example` и подобные шаблоны перечисляют
  каждую переменную, которую читает код.
- Журнал изменений: запись в `.agents/changelog/` по `.agents/rules/changelog.md`
  проекта. Проект без такой папки, но с `CHANGELOG.md` или release notes, ведёт
  их в своём формате; новый журнал wrap-up не заводит.
- Заметки о миграции для всего ломающего: переименованные API, изменения схемы,
  удалённые флаги, изменённые значения по умолчанию.
- Контракты API: OpenAPI, GraphQL schema, protobuf, JSON schema, сгенерированные
  клиенты. Перегенерировать, если генерируются; править, если пишутся руками.
- Документы архитектуры и ADR: новый компонент, удалённый компонент, решение,
  отменившее прошлый ADR. Один короткий ADR лучше длинного абзаца в отчёте.
- Схемы: mermaid или картинки, показывающие старую структуру.
- Runbook'и и ops-документация: новые сервисы, новые алерты, изменённые шаги деплоя.

## Инструкции для агентов и контрибьюторов

`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `.cursorrules` и подобные файлы — для
того, что не выводится из кода. Дописывать в них только если работа дала одно из:

- Договорённость, которой должна следовать будущая работа и которую код не делает
  очевидной.
- Подводный камень, стоивший реального времени: нестабильная команда, порядок
  действий, странность инструмента.
- Команду, которую нельзя найти в `package.json`, `Makefile` или CI.
- Границу: что не трогать, где нужен человек, где тесты медленные.

Не добавлять рассказ о сделанном, список изменённых файлов, пересказ того, что код
уже говорит. Записи короткие, в повелительном наклонении.

## Встроенная документация

- Docstrings и JSDoc изменённых публичных функций соответствуют новой сигнатуре
  и поведению, включая ошибки и крайние случаи.
- Комментарии рядом с изменённой логикой всё ещё верны. Устаревший комментарий хуже,
  чем никакого.
- Заголовки модулей и файлов с описанием назначения всё ещё совпадают.
- Аннотации типов и экспортируемые типы совпадают с реализацией.

## Журналы проекта

Если проект ведёт `.agents/changelog/`, `.agents/decisions/` или `.agents/learnings/`,
их заполнение — обязательная часть wrap-up, а не «по желанию». Правила формата
берутся из проекта: `.agents/rules/decisions.md`, `learning.md`, `changelog.md`
и `AGENTS.md` внутри каталога журнала. Записи идут в тот же коммит, что и код.

- Решение: был выбор между вариантами, и он объясняет, почему код такой. Файл
  `YYYYMMDD_HHMM_statement.md` с `Decision` и `Why` (названные отвергнутые
  варианты) плюс строка в `_TOC.md`. Пересмотр старого решения — новый файл со
  ссылкой на прежний, прежний не переписывается.
- Learning: факт вопреки документации или ожиданию, проверенный командой, путём
  или логом. Файл с `Expected`, `Actual`, `Verified`, `Do` плюс строка в `_TOC.md`.
  Непроверенное — одна строка в «Hypotheses». Факт по дороге к решению — раздел
  `Trap` этого решения.
- Changelog: изменение, которое заметит пользователь или оператор. Файл
  `YYYYMMDD_HHMM_short_statement.md` в `.agents/changelog/`, его создаёт рецепт
  проекта (`just changelog add`): дату с временем и поясом ставит он. `type` из
  шести (`Добавлено`, `Изменено`, `Устарело`, `Удалено`, `Исправлено`,
  `Безопасность`), тело одной строкой до 200 символов, результат для читателя
  снаружи. Несовместимое помечено `breaking: true`, и строка говорит, что делать.
  Решение называется в поле `decision`, ссылки на план нет. Продолжение прежней
  записи правит её файл, имя не меняется.
- Проверка перед отчётом: у каждого пункта плана из «Definition of done»,
  видимого снаружи, есть запись в changelog (или явное «ничего не изменилось
  снаружи» в плане); у каждого решения из «Decision log» плана, пережившего
  план, есть файл.

Пустой ответ допустим, но проговаривается в отчёте: «решений с альтернативой не
было». Журнал, которого в проекте нет, во время wrap-up не заводится.

## Планы и трекинг задач

- Файл плана (при scope «План» или «Сессия»): каждый пункт отмечен как сделано,
  отложено с причиной или снято с причиной. Добавить строку «Статус» с датой.
  Отложенное становится follow-up в отчёте.
- Todo-списки внутри репозитория (`TODO.md`, GitHub issues, на которые ссылается
  код): закрыть или обновить те, что эта работа решила.
- Трекер задач: закрывающий комментарий с тем, что изменилось и как проверить, если
  проект пользуется трекером и пользователь там работает.
- Описание PR: соответствует финальному diff, содержит как тестировать, ссылается
  на issue.

## Метаданные скиллов и инструментов

Когда работа касалась скилла, плагина или общего инструмента:

- Frontmatter `SKILL.md` всё ещё описывает поведение; версия поднята, если проект
  версионирует скиллы.
- `meta.json` (в репозитории скиллов): `modified: true` и заметка с описанием правки,
  если скилл из upstream; для своих и derived скиллов обновить `notes`
  и `source.from[].ref`, где это уместно.
- Симлинки на скилл по-прежнему разрешаются.

## Постоянная память

Когда harness даёт память между сессиями, хранить долговечные факты, а не журнал
изменений. Стоит сохранить:

- Предпочтения и поправки пользователя, данные по ходу работы («без таблиц
  в скиллах», «всегда uv»), с объяснением почему.
- Ограничения проекта, которых нет в репозитории: сроки, кто за что отвечает, какие
  окружения существуют, что нельзя трогать.
- Решения с их обоснованием, когда код не делает обоснование очевидным и ADR нет.
- Ссылки на найденные внешние ресурсы: дашборды, тикеты, страницы документации.

Не стоит сохранять: списки файлов, что сделал diff, всё, что git или кодовая база уже
фиксируют. Перед записью проверить, нет ли памяти на ту же тему, и обновить её вместо
создания почти-дубликата.

## Отчёт

По каждому тронутому документу: файл и одна строка о том, что изменилось. По
рассмотренным и оставленным без правок — ничего, кроме случаев, когда пользователь
ждал бы обновления («README не менял: флаг внутренний, не пользовательский»). Если
документу нужен продуктовый или командный ответ, вынести в follow-up с вопросом,
на который нужно ответить.
