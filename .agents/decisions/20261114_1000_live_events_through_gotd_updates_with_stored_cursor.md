# Живые события идут из менеджера обновлений gotd через журнал SQLite с курсором по id, subscribe шлёт уведомления, message watch печатает jsonl

Decided: 2026-11-14
Revised: —

## Context

Агент узнавал о новых сообщениях только опросом `message history`: это нагружает аккаунт, шумит в дросселе и теряет события, пока агент не смотрит. Пункты 2.4 и 8.1 до 8.4 в `FEATURES.md` оставались без реализации; пункт 2.4 попал сюда из решения [без `execute`](20261114_0033_execute_is_not_built.md).

Проверенные факты gotd/td v0.166.0: `updates.Manager` сам реализует `telegram.UpdateHandler`, хранит `pts`, `qts`, `date`, `seq` и `pts` каналов в `StateStorage`, сам вызывает `getDifference` и `getChannelDifference`, а его запросы идут через `c.tg.API()`, то есть через [дроссель](20261114_0310_throttle_one_account_gate_60_percent_three_levels.md). Без сохранённого состояния он берёт состояние с сервера. `UpdateDeleteMessages` (личные чаты и обычные группы) несёт только список id сообщений, без чата. [Фильтр чатов](20261114_0900_access_lists_hide_chats_and_untrusted_text_is_marked.md) требует не отдавать события закрытых чатов, а сам назвал фильтр потока условием пересмотра.

## Decision

- Источник. Daemon запускает менеджер обновлений gotd после входа в аккаунт; `*peers.Manager` служит хранилищем хешей доступа. Состояние менеджера лежит в таблице `account_state`: ключи `updates.state.<userID>` и `updates.channel.<userID>.<channelID>`. Первый запуск без состояния идёт «с этого момента», историю не догружает.
- Типы событий: `message.new`, `message.edit`, `message.delete`, `reaction` (хранятся), `read`, `typing`, `status` (живые, не хранятся и не воспроизводятся), `gap` (менеджер не смог восстановить пропуск, а также устойчивый сбой записи события, `reason: "store"`) и `lagged` (подписчик не успевает).
- Журнал. Таблица `events` (миграция `0003_events.sql`): `id` (`AUTOINCREMENT`), `type`, `chat_id`, `created_at`, `payload` (JSON), уникальный `dedup_key` (`new:`, `edit:`, `del:`, `react:` с идентификаторами). Запись с тем же `dedup_key` не создаёт второй строки. Хранение: 7 суток или 100 000 событий, что наступит раньше; очистка при старте и раз в час. Сообщения из потока пишутся и в `messages` (правка сохраняет прежнюю версию, удаление с известным чатом ставит `deleted_at`), поэтому локальный поиск видит поток.
- Курсор. Строка `<id>.<pts>.<qts>.<date>`. Для продолжения важен только ведущий `id`; тройка берётся из состояния менеджера на момент выдачи курсора и информационная. `id` последнего события, удалённого очисткой, сохраняется в `account_state` под ключом `events.high_water`, поэтому курсор последнего удалённого события остаётся допустимым. `after` старше границы хранения даёт ошибку `cursor_expired` (код RPC -32007, код выхода 8).
- Метод `subscribe` (JSON-RPC). Параметры `chats`, `topic`, `types`, `after`; ответ `subscription_id` и стартовый `cursor`. События приходят уведомлениями без `id`, метод `event`. Одна подписка на соединение, вторая даёт `busy`. Закрытие сокета или `unsubscribe` снимает подписку. Очередь подписчика 1000 событий: при переполнении приходит `lagged` с курсором последнего доставленного и подписка закрывается, события остаются в журнале. Подписка без `after` стартует с текущего момента; с `after` Daemon отдаёт сохранённые события, затем живые, без разрыва и повторов. Активный подписчик не даёт `--idle-timeout` остановить Daemon.
- Фильтр чатов. События закрытых чатов отбрасываются до записи в `events` и до доставки, включая `typing`, `read` и `status` (чатом `status` считается личный чат пользователя); политика применяется и при воспроизведении. `message.delete` для личных чатов и обычных групп приходит без `chat_id`: при включённом фильтре чат определяется по локальной базе (`chat_id` ставится, если сообщения одного чата), а неопределимый или закрытый чат отбрасывает событие; без фильтра событие идёт без `chat_id`. `gap` без чата проходит всегда и все фильтры подписки. `--chat` разрешается только по локальной базе (чат уже прочитан Daemon), закрытая или неизвестная ссылка даёт один и тот же `not_found`. `--topic` оставляет только `message.new` и `message.edit` топика.
- CLI. `message watch [--chat <ссылка>]... [--topic N] [--types a,b] [--after <cursor>] [--max-events N]`, класс безопасности «чтение». Формат по умолчанию `jsonl`: событие целиком в одной строке, без конверта. `--format json` допустим только с `--max-events` (конверт `{"ok":true,"data":{"events":[...]}}`), `--format toon` отклоняется кодом 2. Подсказка `watching from cursor <cursor>` идёт в stderr.

## Why

- Менеджер gotd, а не опрос `getDifference` из CLI. Менеджер уже ведёт состояние и правила разрыва, а CLI не обращается к Telegram сам. Отвергнуто: свой опрос из CLI, он потребовал бы своё состояние и вторую точку доступа к сессии.
- Журнал в SQLite, а не только в памяти. Продолжение с курсора между сессиями (8.3) требует, чтобы события пережили остановку Daemon, а `lagged` без журнала терял бы события. Отвергнуто: хранение только в памяти.
- Курсор по `id`, а не `{pts,qts,date}`. Тройка описывает состояние сервера, а не позицию в нашем журнале: у каналов свой `pts`, и по тройке нельзя воспроизвести журнал с фильтром по чатам. `id` возрастает и однозначно упорядочивает журнал. Тройка осталась в строке для сверки с пунктом 8.3.1. Отвергнуто: курсор из `{pts,qts,date}`.
- Курсор из одного `id` без тройки отвергнут: пункт 8.3.1 называет тройку, поэтому она осталась в строке, хотя продолжение от неё не зависит.
- Срок 7 суток или 100 000 событий держит размер базы; числа взяты из рекомендации плана и на живом потоке не измерены. Отвергнуто: 30 суток (больше база без подтверждённой нужды) и хранение без границы (база растёт без предела).
- События закрытых чатов отбрасываются до записи, а не скрываются при выдаче: закрытое не должно лежать в базе. Отвергнуто: писать всё и фильтровать при выдаче.
- `typing`, `read` и `status` живые. Это мгновенные сигналы, их воспроизведение после разрыва агенту не нужно, а место в журнале ограничено. Отвергнуто: хранить всё.
- Состояние менеджера в `account_state`: таблица уже есть, новая миграция не нужна. Отвергнуто: отдельная таблица `updates_state`.
- Одна подписка на соединение: метод проще, а второй поток открывает второе соединение. Очередь 1000 и `lagged`, а не блокировка: медленный подписчик не тормозит обработку обновлений. Отвергнуто: очередь 10000, она держит больше памяти ради редкого случая.
- Первый запуск «с этого момента»: поток нужен для нового, а догрузка последних N это глубокая загрузка истории (10.12), отдельная задача. Отвергнуто: догрузка последних N.
- `jsonl` без конверта и без `toon`: поток бесконечен, строки читаются независимо, а TOON печатает ответ целиком. `--max-events` нужен скриптам и тестам, через него работает `--format json`.

## Cost

- Приёмник событий не возвращает ошибку менеджеру. При устойчивом сбое записи (три повтора) состояние менеджера может продвинуться, а событие потеряться; агент увидит `gap` с `reason: "store"`. Опция менеджера `StopOnApplyError` включена, но не защищает, пока приёмник не возвращает ошибку; строгий порядок «событие, потом состояние» потребует изменить интерфейс приёмника. Условие пересмотра.
- `gap` оставляет пропуск агенту: для `ChannelDifferenceTooLong`, недоступных каналов и устойчивого сбоя записи он читает историю командой `message history` сам. Причины `reason`: `channel_too_long`, `channel_gap`, `channel_inaccessible`, `too_long`, `store`.
- Хранение 7 суток: агент, молчавший дольше, получает `cursor_expired` и начинает без `--after`. Очищается только `events`; сообщения потока остаются в `messages` как всё прочитанное.
- Удаление в личном чате или обычной группе без известного чата при включённом фильтре отбрасывается: агент может не увидеть такое удаление. Без фильтра оно идёт без `chat_id`, а сообщение в `messages` не помечается удалённым: `search --deleted` такое удаление не найдёт.
- Менеджер работает, пока работает Daemon; `--idle-timeout` его не учитывает, останавливает Daemon без подписчиков по обычному правилу.
- Что не проверено на живом аккаунте: см. [FEATURES.md](../../FEATURES.md) 8.2, 8.3, 8.4. Нагрузка менеджера на SQLite не измерена.
