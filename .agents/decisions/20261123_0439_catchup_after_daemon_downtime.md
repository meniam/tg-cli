# После простоя Daemon догоняет пропущенные сообщения в общей очереди

## Context

Менеджер обновлений gotd восстанавливает пропуски, но при некоторых сбоях сообщает о разрыве, который глубокая загрузка от `oldest_id` не закрывает. Daemon не знал, как давно он не работал. Решение 20261120_1651 и прежний контракт называли `background_sync.enabled` выключенным по умолчанию, но код уже задаёт `true`. Эта запись пересматривает указанное умолчание; само расписание сохраняется.

## Decision

- Daemon пишет Unix-время JSON-числом в `account_state.last_alive_at` раз в минуту и при чистой остановке, только если вход выполнен, клиент готов и нет `auth_lost`. При старте читает прежнюю метку. Без неё и при простое не больше 10 минут автодогонки нет.
- После простоя больше 10 минут догонка выбирает разрешённые чаты с сохранёнными сообщениями, если дата последнего сообщения диалога новее метки минус 10 минут. Она грузит от верха до этой границы или до достижения 1000 сообщений на границе страницы. `chat.history_mode = skip` не учитывается.
- Отдельный ключ `catchup.enabled` и `background_sync.enabled` по умолчанию `true`; догонка работает только при включённых обоих, изменение каждого требует перезапуска. Переменная `TG_CLI_CATCHUP_ENABLED` переопределяет первый ключ.
- Догонка использует тот же `historySyncManager` и общий дроссель. В очереди ручная полоса первая, полоса догонки и автозагрузки нового чата в порядке поступления вторая, фоновая третья. У догонки `source: catchup`, у нового чата остаётся `background`. Постановка догонки не прерывает идущую фоновую задачу; ручной `start` не отменяет догонку, но отменяет задачи `background` по прежнему правилу.
- Перед каждой страницей догонки, включая первую, действует пауза планировщика. `tg chat sync catchup [--dry-run]` повторяет выбор с границей из метки, прочитанной при старте этого Daemon, без флага `--since`. Без подходящей метки ответ содержит `since: null` и задач нет.

## Why

- Граница по времени использует свежесть диалога: `newest_id` отстаёт от живых сообщений и может привести к ложному пределу. Запас покрывает время между последней меткой и аварийным выходом.
- Один воркер сохраняет общий темп, отмену и статус; отдельный воркер мог бы обойти ограничение параллелизма. Пауза перед первой страницей распределяет запросы даже у чатов в одну страницу.
- Отдельный выключатель позволяет отключить догонку, сохранив расписание; общий выключатель остаётся обязательным. Отвергнут единый выключатель без возможности разделить эти действия.
- Отвергнуты отмена догонки ручным `start` и прерывание идущей глубокой загрузки ручной догонкой: задачи остаются, а порядок ожидания понятен. Отвергнут `source: background` для догонки: такую задачу ошибочно отменял бы конец окна.
- Для ручного повтора выбрана граница старта, а не новый флаг `--since`; произвольный период задаёт `chat sync queue --since`. Отвергнут учёт `skip`: он относится к глубокой загрузке, как и у автозагрузки нового чата.

## Cost

- Догонка включена по умолчанию; чат с `skip` тоже получает догонку. Глубокая загрузка по расписанию ждёт окончания активных задач; новый чат может ждать догонки, поставленные раньше.
- Оценка по коду, не измерение: для 300 активных чатов обход диалогов потребует около 3-4 запросов, а 450-600 страниц с паузой 2-8 секунд могут занять около 40-50 минут.
- Готовность клиента не отражает разрыв уже работающего Daemon: долгий обрыв связи сам по себе догонку при следующем старте не включает. Событие `gap` её тоже не ставит. Пропущенные удаления и события правок может вернуть только менеджер обновлений; страницы истории дают текущее состояние.
- После деплоя догонка может запуститься после первого простоя больше порога, когда метка уже создана. При первом запуске нового бинарника метки ещё нет.
