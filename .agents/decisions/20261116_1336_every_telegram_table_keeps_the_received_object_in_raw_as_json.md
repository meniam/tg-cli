# Каждая таблица с данными Telegram хранит полученный объект в raw как JSON

## Context

Колонка `raw` есть у `chats`, `people`, `messages`, `message_versions`, `folders`, но не у остальных таблиц, куда данные приходят из Telegram. В `messages.raw` лежит не ответ Telegram, а JSON, который собрал наш Daemon; `chats.raw` не пишется. Решение о хранилище (2026-11-13) обещало «сырое сообщение целиком». Владелец хочет для всего, что есть, колонку с данными в том виде, в каком мы их получили.

## Decision

- Колонка `raw TEXT CHECK (raw IS NULL OR json_valid(raw))` есть в каждой таблице, чьи строки приходят из Telegram: `chats`, `people`, `messages`, `message_versions`, `folders`, `chat_versions`, `dialog_state`, `account_sessions`, `blocked_peers`, `notify_defaults`, `events`, `transcriptions`.
- Без `raw` остаются собственные таблицы: `notes`, `note_tags`, `sync_state`, `folder_chats`, `idempotency`, `meta`.
- Формат: JSON по общему правилу, не бинарный TL. Свой сериализатор объектов gotd помечает тип вложенных объектов ключом `"_"`, пропускает нулевые поля и вырезает `access_hash`.
- Если строка собрана из нескольких ответов, в `raw` лежит объект с этими ответами по именам методов.
- `raw` перезаписывается последним полученным ответом; прошлые значения хранят таблицы версий.
- Закрытые чаты (`block` или вне непустого `allow`) в `raw` не вычищаются: массивы `chats` и `users` ответа и пиры папок хранятся как получены (решение владельца 2026-11-16). Правило «закрытые чаты не сохраняются в базе» в `docs/cli/access.md` меняется: оно относится к строкам таблиц, а не к `raw` разрешённых объектов. Агент не должен получать `raw` ни одной командой.
- Миграция `0009` добавляет колонки через `ALTER TABLE ADD COLUMN` и пропущенную проверку `json_valid` у `message_versions`.

## Why

- Исходный ответ нельзя восстановить из разобранных полей, а поля, которые мы не разбирали сегодня, понадобятся завтра.
- JSON читается в `sqlite3` и ищется через `json_extract`.
- Отвергнуто: бинарный TL в BLOB. Он компактнее (объект сообщения 56 байт) и читается gotd без потерь, но `sqlite3` показывает только байты, нужна отдельная команда просмотра, а `access_hash` остаётся внутри.
- Отвергнуто: JSON и BLOB вместе. Самый большой рост базы и два места, которые надо держать согласованными.

## Cost

- Стандартный `json.Marshal` объектов gotd раздувает вывод нулевыми полями и теряет тип вложенных объектов, поэтому нужен свой сериализатор и тест на отсутствие `access_hash`.
- База вырастет; для сообщений `raw` примерно удвоит строку. Размер не измерен, перед включением на всю историю нужна проверка на копии базы.
- Старые строки получают `raw` при следующем чтении из Telegram. В `messages.raw` до тех пор лежит JSON Daemon; новый формат отличается ключом `"_"`.
- `file_reference` в `raw` остаётся: это не секрет, но он протухает. Окончательно решается в плане.
