# Выгрузка из базы это команда message export --local: Daemon отдаёт страницы до 500 сообщений и 768 КиБ, CLI печатает JSONL по строке на сообщение, версии правок не входят

Decided: 2026-11-14
Revised: —

## Context

Чтобы выгрузить сохранённую историю чата, агент мог листать `message history` (страницы до 100 сообщений, от новых к старым, курсор `next_cursor`, на каждой странице вызов Telegram) или читать окно `message context --local`. Команды, которая отдаёт всё сохранённое из базы одним вызовом, не было. После [глубокой загрузки](20261114_1353_deep_history_sync_is_a_background_job_behind_the_shared_throttle.md) в базе лежат тысячи сообщений чата.

Факты аудита (проверены чтением кода и тестами, на живом аккаунте нет):

- `message.history` требует вход и для имени чата при включённом фильтре вызывает Telegram `Resolve` (`internal/daemon/access.go`, `requireAllowedChat`). `message context --local` разрешает имя только по базе и проверяет фильтр без входа (`localChatID` в `internal/daemon/discovery.go`).
- Кадр RPC не больше `rpc.MaxFrameSize` (1 МиБ). В `message.history` сообщение больше кадра рвёт транспорт, а не даёт ошибку.
- Запрос `WHERE chat_id=? AND id>? ORDER BY id LIMIT ?` идёт по автоиндексу `messages` на `(chat_id, id)` без отдельной сортировки (15 000 строк, SQLite 3.54.0); новый индекс не нужен.
- Версии правок лежат в `message_versions`, поток пишет туда прежний текст при правке (`TestEventEditPersistsMessageVersionForExport`).

## Decision

- Команда `tg message export <чат> --local [--since T] [--until T] [--include-deleted] [--limit N] [--after ID]`, класс `read`. Источник только база: Telegram не вызывается, вход не нужен, Daemon должен работать. Без `--local` код 2 с пояснением, что выгрузка из Telegram не сделана (FEATURES 14.1).
- Daemon: метод `message.export_local` (`internal/daemon/export_local.go`), параметры `chat`, `since`, `until`, `include_deleted`, `after`, ответ `{messages, next_after?}`. `next_after` есть, пока дальше есть сообщения, и равен `id` последнего в странице. Страница не больше `store.MaxExportPageSize` (500) и не больше `maxPageBytes` (768 КиБ, та же константа, что у `message history`): размер считается по `{"messages":[]}`, закодированным элементам, запятым и `,"next_after":N`, остаток до кадра идёт на конверт JSON-RPC. `--limit` обрабатывает CLI, в метод он не передаётся.
- Чат разрешается как у `message context --local`: по базе, без Telegram; фильтр закрытых чатов проверяется на каждой странице; неизвестное имя, неизвестный `id` и закрытый чат дают `not_found`.
- CLI (`internal/cli/export_cmd.go`) сам листает страницы и печатает строки по мере получения. Формат по умолчанию `jsonl`: одна строка, одно сообщение, поля `rpc.Message` (как у `message context --local`) и `deleted: true` только у удалённых; `human` разрешён (чужой текст в рамке), `json` и `toon` дают код 2. Порядок по возрастанию `id`.
- По умолчанию удалённые скрыты (`deleted_at IS NULL`), `--include-deleted` включает их. `--after` продолжает выгрузку (`id` строго больше). Сообщение, которое не помещается в страницу, даёт код 1 и текст `message <id> does not fit into a response page`, без текста сообщения.
- Подсказка stderr после выгрузки: `exported N locally saved messages; check completeness with tg chat sync status <chat>`; при обрыве после напечатанных строк: `last exported id: N; resume with --after N and the same filters`. `--quiet` скрывает обе.

## Why

- Новая команда, а не `message history --local`: порядок обратный (от старых к новым), страница и курсор другие, у `history` лимит 100 и вызов Telegram по умолчанию. Один флаг менял бы порядок, формат ответа и требование входа. Отвергнуто: `message history --local`.
- Страницы Daemon и листание в CLI, а не один ответ: чат на тысячи сообщений не помещается в кадр 1 МиБ. Отвергнуто: один ответ Daemon.
- Бюджет 768 КиБ вместе с 500 сообщениями, а не только число: сообщение с большим сырым JSON раздувает страницу выше кадра. Одна и та же константа с `message history` оставляет запас на конверт.
- Явная ошибка с `id`, а не отправка слишком большого сообщения: такая страница всё равно выше кадра, транспорт рвётся, и агент видит код 1 без причины. Отвергнуто: отдать одно сообщение единственным в странице.
- Только `jsonl` и `human`, без `json` и `toon`: это один конверт с полным ответом, а выгрузка печатается по мере получения страниц и не копит чат в памяти; конверт можно было бы напечатать только после последней страницы. Отвергнуто: `json` с конвертом и `toon`.
- Разрешение чата по базе, а не через Telegram: инвариант «без Telegram и без входа» выполнен, как у `message context --local`. Отвергнуто: путь `message history` (вход и возможный `Resolve`).
- Версии правок не входят: строка показывает текущий текст и `edited`, просто и достаточно для агента; версии отдельным решением позже. Отвергнуто: поле `versions` в строке.
- `--local` обязателен, пока нет выгрузки из Telegram: источник один, флаг не вводит в заблуждение, а будущий режим не меняет смысл команды без флага. Отвергнуто: команда без флага, которая читает базу по умолчанию.

## Cost

- Выгрузка не снимок: страницы читаются отдельными запросами, сообщение, сохранённое, правленое или удалённое между страницами, может попасть или не попасть. Закрытие чата между страницами даёт `not_found` посреди потока: уже напечатанные строки верны, после них идёт конверт ошибки.
- Выгружено только сохранённое: полноту показывает `tg chat sync status <chat>` (`complete`), а не сама команда.
- Строка это `rpc.Message` из базы, а не сырой JSON Telegram; `sender.username` в схеме есть, но у сообщений с сохранёнными `id` или именем автора выгрузка его не отдаёт (`rpcStoredMessage` пересоздаёт `Sender`).
- Сообщение больше страницы останавливает выгрузку; обойти его можно только `--after <его id>`, и в выгрузку оно не попадёт. Тестом такое сообщение покрыто, на реальном чате оно не встречалось.
- Не сделано: выгрузка из Telegram, версии правок, файл `--output`, CSV, несколько чатов за раз, фильтр по теме.
- Владелец подтвердил 2026-11-14 форму команды и состав строки (сообщение и признак удаления, версии не входят, удалённые скрыты по умолчанию). Остальные решения (только `jsonl` и `human`, `--local` обязателен, разрешение по базе, бюджет байт и ошибка вместо отправки) ждут подтверждения владельца. Проверено автотестами без Telegram; на живом аккаунте не проверено.
- Условие пересмотра: выгрузка из Telegram, реальный чат с сообщением больше страницы, замеры на большом чате.

## Trap

Признак `deleted` отражает только `deleted_at` в базе. Событие удаления в личном чате и обычной группе приходит без `chat_id`, и при выключенном фильтре (`access.json` без списков) поток `deleted_at` не ставит: `handleEvent` в `internal/daemon/events.go` пропускает поиск чата, а `MarkMessagesDeleted` вызывается только с известным чатом. Одноразовый тест при подготовке документов подтвердил: сообщение осталось без `deleted_at`. Для канала и супергруппы чат есть в событии, и пометка ставится; удаление командой `message delete` тоже ставит её. Это отдельная находка, не часть решения.
