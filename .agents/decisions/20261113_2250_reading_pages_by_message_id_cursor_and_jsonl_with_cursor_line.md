# Чтение страницами с курсором по id сообщения, JSONL с завершающей строкой курсора

Decided: 2026-11-13
Revised: —

## Context

Агенту нужно читать историю чата частями и продолжать между вызовами
(пункт 4.8 в `FEATURES.md`), а списки печатать построчно (пункт 3.2).
Установленная `tg` листает смещением (`--offset`, курсора нет), которое плывёт,
когда между вызовами приходят новые сообщения; `kaosb/tgcli` отдаёт один запрос
без листания; `chigwell/telegram-mcp` листает страницами по смещению и по id с
флагом `has_more`. Telegram отдаёт историю за запрос не более 100 сообщений
(документация и `gotd/td`). Кадр протокола Daemon 1 MiB.

## Decision

- История идёт от новых сообщений к старым. Страница: по умолчанию 20
  сообщений, не больше 100, больше 100 отказ кодом 2.
- Курсор `next_cursor` непрозрачная строка base64url от
  `{v:1, c:<id чата>, i:<id последнего сообщения страницы>}`. Следующая страница
  это сообщения с id меньше `i`. Курсор другого чата и повреждённый курсор
  отклоняются кодом 2.
- Страница обрезается по размеру: когда закодированные сообщения дошли до
  768 KiB (три четверти кадра), страница заканчивается, а курсор указывает на
  остаток. Порог мой, значение подтверждается тестом.
- `--since` и `--until` только в RFC 3339. `--until` задаёт серверное смещение
  по дате (только первая страница), `--since` останавливает чтение на клиенте,
  потому что история идёт от новых к старым.
- Формат списков `--format json|jsonl`. JSON это обычный конверт. JSONL это по
  одному объекту на строку без конверта; если страница не последняя, последняя
  строка `{"next_cursor":"..."}`. Ошибка всегда конверт.
- Чат указывается ссылкой: `@username`, `username`, id в формате Bot API
  (пользователи положительные, группы отрицательные, каналы от
  `-1000000000000`), телефон контакта, ссылка `t.me`. Отрицательный id пишется
  после `--`, иначе парсер флагов примет его за флаг; сообщение об ошибке
  подсказывает это.
- Новый код выхода `7 not_found` и код RPC `-32006`: чат, пользователь или
  сообщение не существуют или не видны аккаунту.
- Читающий код `tgclient` не вызывает методов, которые меняют данные аккаунта:
  это проверяет тест по исходникам.

## Why

- Курсор по id не плывёт при новых сообщениях, в отличие от смещения у `tg`.
- Обрезка по размеру страхует кадр 1 MiB, у `tg` её нет.
- Строка с курсором в JSONL лежит в том же потоке stdout, и по ключу её
  отличить от элементов.
- Отвергнуто: курсор в stderr. Данные в stderr теряются при перенаправлении.
- Отвергнуто: листание смещением. Плывёт при новых сообщениях.
- Отвергнуто: без максимума и со встроенным листанием по 100, как `tdl`.
  Один вызов станет долгим и упрётся в FLOOD_WAIT.

## Cost

- Потребитель JSONL обязан знать про строку `next_cursor`.
- Максимум 100 и порог 768 KiB не измерены на живых данных и не названы
  владельцем (владелец выбрал 20 по умолчанию).
- Формат курсора внутренний: смена формата сделает старые курсоры
  недействительными (версия внутри).
- Числовой id, которого сессия ещё не видела, может не разрешиться до тех пор,
  пока не прочитан список чатов: менеджер адресатов хранит кэш в памяти. Для
  этого при первой неудаче Daemon один раз читает первые 200 диалогов. На живом
  аккаунте не проверено.
