# Daemon говорит по JSON-RPC 2.0 через Unix-сокет

## Context

Daemon держит соединение с Telegram, а CLI и агенты ходят к нему за ответами.
Установленная `tg` уже работает так: JSON-RPC 2.0 по Unix-сокету режима `0600`,
по одному JSON-сообщению на строку; методы `ping`, `status`, `subscribe`,
`shutdown`, `execute` с массивом `argv`, не больше 16 команд одновременно,
кадр до 1 MiB, дедлайн 120 секунд.

## Decision

- Транспорт между CLI, агентами и Daemon: JSON-RPC 2.0, одно сообщение на
  строку, Unix-сокет с правами `0600`.
- Новые события (например, новые сообщения) приходят уведомлениями без `id`.
- Состав методов, самоописание схемы, ключи идемпотентности и параметр аккаунта
  этим решением не закреплены: они определяются в ТЗ.

## Why

- Протокол умещается в одну страницу и читается глазами: запрос и ответ видны
  через `nc` или `socat`.
- Модель понимает JSON без объяснений, клиентом может быть любой язык.
- Поле `id` позволяет вести несколько запросов одновременно, уведомления дают
  живой поток без повторных запросов.
- Схема проверена в `tg`.
- Отвергнуто: gRPC. Типы и стримы встроены, но тяжелее для агента и скрипта,
  не отладить `nc`.
- Отвергнуто: HTTP REST на localhost. Открытый порт и вопросы безопасности,
  стримы только через SSE.
- Отвергнуто: собственный формат. Придётся описывать и поддерживать.

## Cost

В протоколе нет схемы методов и контроля скорости потока: схему и ограничения
потока определяем сами. Unix-сокет привязывает решение к платформам с такими
сокетами; список платформ ещё не определён
([INTENT.md](../../INTENT.md), открытые вопросы).
