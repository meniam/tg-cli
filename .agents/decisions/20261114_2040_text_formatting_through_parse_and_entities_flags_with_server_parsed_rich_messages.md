# Форматирование идёт флагами --parse и --entities у send и edit, RichMessage разбирает сервер, упоминание по id берётся из кэша пиров, в базу пишется итоговый простой текст

Decided: 2026-11-14
Revised: —

## Context

До этого `message send` и `message edit` отправляли только простой текст (`builder.Text`, `Edit(id).Text`), а Daemon сохранял в базу исходный `p.Text`. Агенту нужны жирный, ссылки, цитаты, блоки кода, спойлеры и RichMessage (заголовки, списки, таблицы, формулы).

Факты аудита (чтение gotd v0.166.0, слой схемы 233, и кода; на живом аккаунте не проверялись):

- `messages.sendMessage` и `messages.editMessage` принимают `rich_message`: `InputRichMessageHTML`, `InputRichMessageMarkdown` или `InputRichMessage` из блоков. `rich.HTML` и `rich.Markdown` создают исходник для серверного разбора, а локальные `rich.ParseHTML` и `rich.ParseMarkdown` дают лишь подмножество.
- Смещения сущностей считаются в UTF-16. Разборщик HTML gotd молча теряет неверную ссылку и ошибку разрешителя пользователя.
- Упоминание по id требует `InputUser` с access hash. `store.Person` hash не хранит.
- В прочитанном `tg.Message` поле `Message` самостоятельно, текст RichMessage лежит в блоках.

Живая проверка (2026-11-14, чат «Браин Тест», ревизия 286a7fc плюс исправление упоминаний): сервер принял RichMessage от пользовательского аккаунта в обоих режимах; приняты все режимы; `message get` вернул текст каждого; правка между режимами прошла во все стороны. Упоминание неизвестного id до исправления дало код 5 (`got empty user`), после код 2.

## Decision

- Флаги у `message send` и `message edit`: `--parse html|markdown|rich-html|rich-markdown` и `--entities ФАЙЛ|-` (JSON-массив сущностей). Они взаимоисключающие, без них поведение прежнее байт в байт. Значения `--parse` перечислены в `tg schema`. С `--entities -` stdin занят, текст берётся только из `--text`.
- `html` и `markdown` разбирает gotd (`message/html`, `message/markdown`) в сущности, сообщение уходит обычным `message` с `entities`. Перед разбором HTML свой строгий проход ловит незакрытые теги и неверные ссылки с позицией.
- `rich-html` и `rich-markdown` передают исходник серверу как `InputRichMessageHTML` и `InputRichMessageMarkdown`; локально проверяются только непустой текст и длина исходника не более 4096 символов, пока предел сервера неизвестен. Отказ сервера даёт код 5 `Telegram rejected rich message`.
- `--entities`: типы `bold`, `italic`, `underline`, `strikethrough`, `spoiler`, `code`, `pre`, `blockquote`, `text_url`, `url`, `email`, `phone`, `mention`, `mention_name`, `hashtag`, `cashtag`, `bot_command`, `custom_emoji`, `date_time`; смещение и длина в единицах UTF-16, границы внутри суррогатной пары, нулевая длина и выход за текст дают код 2 до Telegram.
- Упоминание по id (`tg://user?id=N` в HTML и Markdown, `mention_name`) разрешается через кэш пиров сессии, как числовая ссылка на чат; при промахе один раз загружается список диалогов. Неизвестный id даёт код 2 `unknown user id for this session`.
- `--dry-run` вызывает `CheckText` (метод Telegram-клиента без записи) и возвращает `mode`, `plain_length`, `entities`, `rich` вместе с прежними полями. У rich-режимов `plain_length` и `entities` равны нулю, потому что текст разбирает сервер.
- После успешной отправки и правки Daemon сохраняет в базу итоговый простой текст без разметки (клиент отдаёт его во внутреннем поле, не в JSON). У RichMessage это текст блоков из ответа сервера; если ответ его не несёт, при отправке сообщение не сохраняется, при правке строка не меняется, а следующее чтение сохранит его.
- Чтение: сообщение с `rich_message` и пустым `message` отдаётся в `text` как простой текст блоков (абзацы через перевод строки, ячейки таблицы через табуляцию); сущности и разметка при чтении не отдаются.

## Why

- Два флага с взаимным исключением, а не отдельный флаг на режим (`--html`, `--markdown`, `--rich-html`, `--rich-markdown`, `--entities`) и не отдельные команды: один набор способов с перечислением в схеме, неверное значение видно сразу, команды `send` и `edit` не размножаются. Отвергнуто: флаг на режим, команды `send-rich` и `edit-rich`.
- RichMessage разбирает сервер, а не локальные `ParseMarkdown` и `ParseHTML` в блоки: серверный разбор покрывает всю спецификацию (`rich/spec.md`), локальные разборщики подмножество, и расхождение с клиентами Telegram стало бы нашей ошибкой. Отвергнуто: `InputRichMessage` из локально собранных блоков.
- Упоминание через кэш пиров сессии, а не через базу: Telegram требует access hash, `store` его не хранит, а кэш пиров уже обслуживает числовые ссылки на чат. Неизвестный id получает понятный код 2 вместо кода 5 от сервера. Отвергнуто: разрешитель из `store`, полный запрет упоминаний по id.
- Итоговый простой текст в базе, а не исходная разметка: в режимах разбора `p.Text` это разметка (`<b>x</b>`), а не текст сообщения, и в базе он расходился бы с тем, что вернёт `message get`. Отвергнуто: сохранение исходного `p.Text`.
- RichMessage читается простым текстом блоков, а не Markdown и не пустым `text`: пустое сообщение агент не поймёт, а восстановление разметки из блоков потеряло бы структуру без гарантии обратного разбора. Отвергнуто: Markdown из блоков, пустой `text`.
- `--dry-run` через `CheckText`, а не без разбора: агент видит ошибку формата и число сущностей до записи, а проверка не вызывает методов записи Telegram. Отвергнуто: `--dry-run` без разбора, который показывал бы только длину исходника.

## Cost

- Предел длины RichMessage не известен: 4096 символов исходника выбраны осторожно и могут быть и слишком малы, и слишком велики.
- Rich-исходник не проверяется локально: отказ сервера приходит кодом 5 без позиции в тексте; что именно сервер отвергает, не выяснено.
- Для упоминания по id нужен пользователь, которого знает сессия; `--dry-run` с упоминанием может прочитать его из Telegram. Запись при этом не выполняется.
- Форматирование теряется при чтении: агент видит текст без разметки, а вид RichMessage в клиентах Telegram по тексту не восстановить.
- Что не проверено на живом аккаунте: см. [FEATURES.md](../../FEATURES.md) 5.4. Вид сообщений в клиентах владелец ещё не подтвердил.
- Владелец подтвердил 2026-11-14: поддержку всех типов форматирования, включая RichMessage, взаимоисключающие `--parse` и `--entities`, чтение RichMessage простым текстом блоков и оставление режимов с понятной ошибкой, если сервер откажет. Ждут подтверждения владельца: упоминание по id через кэш пиров сессии и сохранение итогового простого текста. Отдельной строки в журнале решений плана нет у серверного разбора RichMessage и у `--dry-run` через `CheckText`, подтверждения владельца по ним нет.
- Условие пересмотра: отказ сервера на реальный предел RichMessage, расхождение вида в клиентах Telegram, ответ владельца по двум нерешённым пунктам.
- Пересмотрено 2026-11-14: владелец выбрал хранить в базе ИСХОДНУЮ разметку (`p.Text` как передан в `--parse` и `--entities`) вместо итогового простого текста. Строки о сохранении итогового текста выше устарели. Повторное чтение сообщения из Telegram заменяет текст и пишет строку в `message_versions`. Код: коммит `6b3d4bd`.
