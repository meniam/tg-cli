# Имя автора живого сообщения берётся из таблицы people, а старые строки дополняет миграция 0015

## Context

Базовая группа присылает сообщение коротким обновлением `UpdateShortChatMessage` только с id автора. gotd превращает его в `UpdateShort` без списков `Users` и `Chats` (`telegram/updates/conv_shorts.go`, v0.166.0), поэтому `senderOf` в `internal/tgclient/message.go` не находит пользователя и оставляет id без имени. Событие с пустым именем попадало в `events`, в `messages` и к подписчикам `tg watch`. Замер 2026-11-24 на живой базе: из 667 817 сообщений у 2648 есть `sender_id` без `sender_name`, у 1332 из них имя есть в `people`. В чате «4P HR Core» безымянными были 118 из 235 сообщений с 1 ноября, все после 1090463, последнего сообщения фоновой загрузки. Чтение истории возвращает имена и дополняет строки сама (`mergeMessage`).

## Decision

- `daemon.withSenderName` (`internal/daemon/events.go`) вызывается в `handleEvent` для `message.new` и `message.edit` до `addEvent`. Если у автора `id > 0` и нет имени, она читает `people` по id и пишет в `sender.name` «имя фамилия», а при их отсутствии `username`; пустой `sender.username` заполняется тоже. Нет человека или нет имени: байты события не меняются.
- Событие, строка `messages` и доставка подписчикам получают одно и то же имя, потому что `event.Data` заменяется до всех трёх.
- Миграция `0015_sender_names.sql` один раз заполняет `messages.sender_name` у строк с `sender_id > 0` и пустым именем из `people` по тому же правилу. Существующее имя не заменяется. `search_text` сообщения хранит только текст, индексы не пересобираются.
- Запросов в Telegram нет.

## Why

- Данные уже в базе: `people` пополняется при каждой загрузке истории и чтении участников. Чтение одной строки по первичному ключу дешевле запроса `users.getUsers` и не идёт под дроссель.
- Правка в демоне, а не в `tgclient`: `tgclient` не импортирует `store` и не видит `people`.
- Имя подставляется до записи события: журнал `events`, подписчики и `messages` не расходятся.
- Проверка миграции на копии живой базы: безымянных с `sender_id > 0` 2648 до, 1316 после; в «4P HR Core» 0.

## Cost

- Имя это текущее имя человека, а не имя на момент сообщения. Переименованный человек оставит новое имя в старых строках, которые заполнила миграция.
- Автор, которого нет в `people` (1316 строк на 2026-11-24), остаётся без имени, пока чтение истории не вернёт его. Среди них 726 сообщений одного пользователя супергруппы: у них другая причина, она не исследована.
- Миграция меняет строки живой базы за один проход: перед деплоем нужен бэкап, как при прошлых миграциях.

## Rejected

- Запрос `users.getUsers` для неизвестного автора с кэшем: закрыл бы остаток, но добавляет сетевой запрос под дроссель на каждого нового автора. Откладываем до замера остатка после этой правки.
- Читать имя из `people` при чтении сообщения (JOIN в экспорте и поиске): лечит всё без миграции, но имя остаётся пустым в событиях `tg watch` и в самой базе.
- Ничего не менять и ждать загрузки истории: `tg watch` и веб-просмотр продолжили бы получать живые сообщения без имён.
