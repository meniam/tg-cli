# Лимит сообщений чата: подчистка удаляет самые старые и оставляет 95% лимита

## Decision

- Лимита по умолчанию нет. Владелец задаёт его для одного чата: `chat limit set <чат> <N>` (N от 100 до 100000000), `chat limit off`, `chat limit list`. Лимит лежит в `account_state` под ключом `chat.message_limit.<chat_id>`, как `chat.history_mode.<id>`, без миграции.
- Подчистка идёт в Daemon: при старте, раз в час (`chatLimitEvery`) и сразу после `set`. Если в чате строк `messages` больше лимита (удалённые пометкой тоже считаются), `store.TrimChatMessages` удаляет самые старые по `(date, id)` до 95% лимита пачками по 2000 строк, по транзакции на пачку. Вместе с сообщением уходят строки `message_versions`, `transcriptions` и `voice_queue` (задача в состоянии `running` остаётся). Заметки остаются. FTS обновляет триггер `messages_stem_ad`, векторы убирает следующий проход семантического индекса.
- Чат, закрытый списками доступа, подчистка пропускает.
- Подчищенный чат получает `complete = 1` через `MarkHistoryLimitReached` (`first_message_date` пустая): иначе планировщик и ручная загрузка тянули бы удалённое снова, и подчистка удаляла бы его снова. Полная загрузка чата с лимитом останавливается на его лимите вместо `history_limit.messages`; дата `history_limit.since` действует как прежде.
- `chat limit set` удаляет данные насовсем и поэтому помечена `dangerous`: если в чате сообщений больше лимита, команда без `--yes` отвечает кодом 2 с `saved` и `will_delete` и ничего не меняет.

## Why

- 95% вместо ровно лимита: подчистка не запускается после каждого нового сообщения, а срабатывает редко и режет сразу пачку (запрос владельца).
- Подчистка по таймеру и после `set`, а не при каждой записи: запись сообщения остаётся быстрой, лишнее место в базе живёт не дольше часа.
- Отвергнуто: пометка `deleted_at` вместо удаления строк. Размер базы не уменьшился бы, а цель лимита в нём.
- Отвергнуто: таблица `chat_limits` с миграцией. Один ключ на чат уже есть как образец (`chat.history_mode.`), выборка по префиксу простая, миграция добавила бы схему 14 ради одного числа.
- Отвергнуто: лимит как настройка профиля для всех чатов. Владелец просил лимит по чатам; общий предел уже есть в `history_limit.messages`.
- Отвергнуто: подтверждение через список доступа владельца. `--yes` по образцу `message delete` проще и достаточно: команда локальная и не касается Telegram.

## Cost

- Удалённые сообщения из базы не вернуть. Telegram их хранит, но чат помечен `complete`, а команды сброса нет, поэтому загрузка не возьмёт их заново. Снятие лимита чат не открывает.
- Раз в час и при старте Daemon читает все лимиты и считает строки каждого лимитного чата.
- Заметки остаются и могут указывать на удалённое сообщение.
- Подчистка не знает, что сообщение закреплено или важно: удаляет по возрасту.
