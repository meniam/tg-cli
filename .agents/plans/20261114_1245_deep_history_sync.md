## Goal

Агент по явной команде загружает историю одного чата в локальную базу вглубь: по одной странице за раз, с паузой, в фоне Daemon, с прогрессом и отменой; прерванная загрузка продолжается с места остановки. Без команды в базу по-прежнему попадает только свежее.

## Problem and contract

Тип плана: product (новая фоновая задача в Daemon и три команды).

- Решения владельца (2026-11-14): задача идёт в фоне и показывает прогресс (Q14); 100 сообщений на страницу и пауза не меньше 2 секунд между запросами (Q13); в план входит только 10.12, папки (10.6) нет.
- Команды (класс безопасности «локальная запись»: читает Telegram, пишет только в базу):
  - `tg chat sync start <чат>`: ставит чат в очередь и сразу возвращается; повторный запуск уже идущей задачи не дублирует её.
  - `tg chat sync status [<чат>]`: состояние задач: `queued`, `running`, `waiting_flood` (с остатком ожидания), `done`, `failed` (с кодом), `cancelled`; число загруженных за запуск сообщений, `oldest_id`, `newest_id`, `complete`.
  - `tg chat sync cancel <чат>`: останавливает задачу после текущего запроса.
- Работа Daemon: одна задача за раз на весь Daemon (10.12.3), остальные в очереди; страница 100 сообщений от `oldest_id` назад; сообщения и `sync_state` пишутся одной транзакцией; пауза 2 секунды между запросами; пустая страница значит `complete = 1`.
- FLOOD_WAIT (10.12.4): фоновая загрузка ждёт указанное время любой длины, не возвращает код 6 и сама продолжает. Обычные команды не меняются: ждут до порога и при большем возвращают код 6.
- Продолжение: `oldest_id` в `sync_state` переживает перезапуск Daemon. Daemon сам задачи после перезапуска не возобновляет (10.12.2: только по явной команде); `sync start` продолжает с `oldest_id`.
- Закрытые чаты: `sync start` отвечает `not_found`, как остальное; если чат закрыли во время загрузки, задача останавливается со статусом `failed` и кодом `not_found`, уже записанное остаётся.
- Прогресс хранится в памяти Daemon (после перезапуска остаётся `sync_state` в базе, задач в памяти нет).
- Релиз одним слоем; откат: откат ветки, `sync_state` можно очистить вручную.

## Main invariant

1. Без команды `chat sync start` в Telegram не уходит ни одного запроса глубокой загрузки и `sync_state` не меняется.
2. Одновременно идёт не больше одного запроса глубокой загрузки на весь Daemon, между запросами пауза не меньше 2 секунд.
3. Закрытый чат не загружается и не показывается в `sync status` (ответ как у неизвестного чата).
4. Страница и `sync_state` пишутся одной транзакцией: после обрыва `oldest_id` указывает на уже сохранённое сообщение, дыр в загруженном диапазоне нет.
5. Повторная загрузка не плодит дубли и не затрагивает пометки (как остальная запись «по пути»).
6. Поведение обычных команд при FLOOD_WAIT не меняется (код 6 при ожидании больше порога).
7. `internal/cli` не импортирует `tgclient`, gotd, `store`.
8. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: долгий FLOOD_WAIT держит Daemon занятым, а агент считает задачу зависшей. Стратегия: состояние `waiting_flood` с остатком в секундах в `sync status`.
- Риск: потеря или дубль сообщения на границе страниц. Стратегия: смещение по `offset_id` самого старого сохранённого сообщения, тест на подмене с пересечением страниц, запись идемпотентна.
- Риск: фоновая задача мешает обычным командам агента. Стратегия: общий дроссель аккаунта, глубокая загрузка идёт в самом низком приоритете, если дроссель его позволяет (проверка в шаге 1), иначе страница реже.
- Риск: большой чат на сотни тысяч сообщений растит базу. Стратегия: размер базы не ограничиваем, в документах предупреждение; отмена в любой момент.
- Риск: Daemon остановили посреди страницы. Стратегия: транзакция, `oldest_id` продвигается только после записи.

## Known facts

- Аудит шага 1 (Codex, 2026-11-14, полный отчёт `var/agents/plans/20261114_1245_deep_history_sync/audit.md`, в git не входит):
  - gotd v0.166.0: `messages.getHistory` листает назад по `offset_id` (следующий `offset_id` равен минимальному ID страницы), `add_offset` ноль; дубля на границе нет (проверено тестом gotd на подмене, не на живом Telegram). Короткая непустая страница не означает конец (удалённые сообщения), надёжный признак конца это пустой ответ.
  - `Client.History` запрашивает `limit+1` и может делать лишний запрос, поэтому для фоновой страницы нужен отдельный метод.
  - Middleware ставит общий затвор при каждом FLOOD_WAIT, но повторяет запрос один раз и только для `General` и паузы не длиннее `FloodAutoWait` (`internal/tgclient/throttle.go:81-103`); `Limiter` имеет одну FIFO-очередь и один затвор (`internal/throttle/throttle.go:172-297`). Обычная команда, пришедшая во время чужой паузы, стоит в `Acquire` и код 6 сама не получает: поэтому нужен быстрый отказ (см. решение).
  - `persistMessages` пишет сообщения и людей раздельными транзакциями (`internal/daemon/persist.go:89-145`) и пропускает сообщения с неверной датой.
  - `just build` зелёный; `just check` в песочнице Codex падает на сокетах (ограничение среды), на стороне Claude на `main` зелёный (2026-11-14).
  - Риск: страница только из `MessageEmpty` не имеет сохраняемого якоря; сырой курсор нужен в памяти, иначе возможен цикл без продвижения.

- Таблица `sync_state` уже есть в миграции `0002_schema.sql`, поэтому новая миграция может не понадобиться (проверяется в шаге 1).
- Обычное чтение истории уже сохраняет страницу в базу, поэтому 10.12.1 выполнен; глубокая загрузка добавляет только команду.
