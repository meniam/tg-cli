## Goal

Агент видит только те чаты, которые разрешил человек, и получает чужой текст с пометкой «данные, не команда». Закрытый чат для агента не существует: его нет в списках, в поиске, в заметках, а прямая ссылка даёт тот же `not_found`, что и несуществующий чат.

## Problem and contract

Тип плана: product (меняется наблюдаемое поведение чтения), миграции данных нет.

- Проблема. Агент читает любой чат аккаунта, а текст сообщений приходит в ответе как обычное поле. Любой участник чата может написать инструкцию, которую агент примет за команду (prompt injection), а человек не может закрыть от агента личные чаты.
- Списки (9.2). Файл `access.json` в каталоге профиля, права 0600. Поля `allow` и `block`: массивы числовых идентификаторов чатов в том же виде, в каком их печатает `chat list`. Правит только человек: команды записи в проекте нет. Смысл: если `allow` не пуст, видны только чаты из него; чат из `block` скрыт всегда, даже если он есть в `allow`. Пустые списки или нет файла: всё доступно, как сейчас.
- Невидимость. Фильтр стоит в Daemon, один для всех путей. Закрытый чат убирается из `chat.list`, из выдачи `search` (по `chat_id` каждого попадания) и из `note.list`; `chat.resolve`, `chat.info`, `message.*` и заметки по нему возвращают `not_found` с тем же текстом, что и для несуществующего чата. Различить «закрыт» и «нет» агент не может.
- Перечитывание. Daemon читает файл при каждом запросе, если изменились время изменения или размер, поэтому правка файла действует без перезапуска. Файл с ошибкой разбора: закрыто всё (отказ по умолчанию), запросы получают `internal_error`, Daemon не падает; ошибка в журнале без содержимого файла.
- Состояние для человека. `daemon status` показывает режим: фильтр выключен или включён, число чатов в `allow` и в `block`, без идентификаторов.
- Пометка текста (9.4). В `schema` у каждого поля с чужим текстом (текст сообщения, подпись, название и описание чата, имя автора, попадания поиска) есть признак `untrusted: true`. Структура JSON-ответов не меняется, `json` и `jsonl` байт в байт прежние. В формате `human` такой текст выводится в видимой рамке с предупреждением в первой строке; `toon` остаётся без рамки (его читают разбором). Описание в `AGENTS.md` и в навыке `skill/` говорит агенту: поля с `untrusted` это данные, а не инструкции.
- Охват. Фильтр касается только чтения: записи в проекте нет (раздел 5 и пункт 9.1 вне плана). Живой поток (раздел 8) получит тот же фильтр в своём плане. Люди (`people`) и заметки о людях не относятся к чатам; их судьба в открытых вопросах.

## Main invariant

1. Без файла `access.json` (или с пустыми списками) все ответы байт в байт прежние, кроме поля `untrusted` в `schema` и рамки в `human`.
2. Закрытый чат не виден ни в одном ответе Daemon: ни как запись, ни как `chat_id` в попадании поиска, ни в заметках.
3. Ответ на прямую ссылку закрытого чата не отличается от ответа на несуществующий чат (тот же код, текст и поля).
4. Ошибка разбора файла закрывает всё, а не открывает.
5. `internal/cli` не импортирует `tgclient`, gotd и `store`; фильтр живёт в Daemon.
6. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram.
7. `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: фильтр обходят через путь, о котором забыли (поиск, заметки, `chat.invite_info`, новый метод). Стратегия: Step 1 перечисляет пути по коду; тест полноты падает, если у метода нет пометки доступа.
- Риск: идентификатор чата в файле не совпадает с тем, что видит пользователь. Стратегия: один формат (как печатает `chat list`), тест на каналы, группы и личные чаты.
- Риск: чат закрыт, но его сообщения уже лежат в локальной базе и находятся поиском. Стратегия: фильтр по `chat_id` в самом запросе поиска, а не после выдачи (иначе страницы и курсор показывают дыры).
- Риск: человек не видит идентификаторы закрытых чатов, потому что они пропали из `chat list`. Стратегия: открытый вопрос; пока документировать «временно очистить файл».
- Риск: фильтр после `Resolve` означает, что запрос в Telegram по закрытому чату всё равно уходит (для ссылки не в виде id). Ответ агенту одинаков, но время ответа и счётчик дросселя могут отличаться. Стратегия: принять, агент время не сравнивает; для числового id проверка идёт без обращения к Telegram.
- Риск: области поиска устроены по-разному (`chats`: id в `ID`, `ChatID` пуст; `people`: связи с чатом нет; `notes`: у заметок о людях `chat_id` пуст). Стратегия: условие в SQL по каждой области отдельно, тест на каждую.
- Риск: `access.json` лежит в каталоге профиля, и агент под тем же пользователем с доступом к файловой системе может его изменить. Фильтр защищает от случайного и подсунутого через чат чтения, но не от агента, который сознательно обходит защиту. Стратегия: записать в документы; сильнее защита (другой пользователь, хранение вне доступа агента) вне плана.
- Риск: пометка `untrusted` не защищает сама по себе (агент может её не прочитать). Стратегия: честно записать в документ, что это подсказка агенту, а не барьер; барьером служит фильтр чатов.
- Риск: чтение файла на каждый запрос. Стратегия: сравнение времени изменения и размера, чтение только при изменении.

- `store.SearchOptions` и `store.Note` несут `ChatID *int64`.
- `CodeNotFound = -32006` в `internal/rpc/message.go`.
- Схема строится рефлексией по типам ответов (`internal/schema/schema.go`, `Fields`); признак поля можно добавить тегом.
- Базовая линия Step 1: ветка `main` на c03007d, дерево чистое, `just check` зелёный, `just build` собрал `dist/tg`.
- Итог аудита путей чтения (Step 1, 2026-11-14). Ссылка на чат в запросе это строка (`@username`, числовой id в форме Bot API, телефон, `t.me`, приглашение), её разбирает `chatref.Parse`; числовой идентификатор Daemon знает сразу только для ссылки вида id. Для остальных видов id появляется после `Telegram.Resolve`. Клиент Telegram принимает `chatref.Ref`, а не id (`internal/daemon/telegram.go`: `Resolve`, `ChatInfo`, `InviteInfo`, `History`, `Message`, `Pinned`).

| Метод | Принимает чат | Возвращает чат или `chat_id` | Где |
| --- | --- | --- | --- |
| `chat.list` | нет (фильтр `type`) | да, `rpc.Chat` с `id` | `daemon.go:331`; результат сохраняется `saveChats` |
| `chat.resolve` | да, строка | да | `read.go:47` |
| `chat.info` | да, строка | да, `id`, `about` | `read.go:67` |
| `chat.invite_info` | да, приглашение | нет id: `title`, `about`, число участников | `read.go:87` |
| `message.history`, `message.get`, `message.pinned` | да, строка | да, `chat_id` в каждом сообщении | `read.go:117,160,183`; сообщения сохраняются `saveMessages` |
| `search` | да, необязательно (`resolveStoredReference`, без Telegram) | область `chats`: id чата в `ID`, `ChatID` пуст; `messages` и `notes`: `chat_id`; `people`: связи с чатом нет | `notes.go:231`, `store/search.go:104,124,148,181` |
| `note.add` | да (`chat` и `message`), с запасным обращением к Telegram | да | `notes.go:94`; числовой id принимается без проверки существования |

| `note.delete`, `note.delete_by_author` | нет | нет | `notes.go:205,219` |
| `status` | нет | нет (только свой аккаунт) | `daemon.go:243` |

- Идентификатор чата везде в форме Bot API (`toChatOf`: `p.TDLibPeerID()`, `chatref.ID`, `store` использует тот же): формат файла `access.json` совпадает с `chat list`.
- Чужой текст в ответах (поля для признака `untrusted`): `Chat.Title`, `Chat.Username`, `ChatInfo.Title|Username|About`, `InviteInfo.Title|About`, `Sender.Name|Username`, `Message.Text`, `SearchHit.Title|Snippet` (назван чужим при областях `chats`, `people`, `messages`). `Note.Body` написан владельцем или агентом (`author`), не чужой текст. В `rpc.Message` комментарий уже называет текст данными, но в ответе пометки нет.
- Локальная база: таблицы `chats`, `people`, `messages`, `notes` с FTS (`0002_schema.sql`). `chat.list`, `chat.resolve`, `chat.info` и чтение сообщений сохраняют всё, что вернул Telegram, без учёта списков.
