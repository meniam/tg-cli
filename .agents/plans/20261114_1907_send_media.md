## Goal

Агент отправляет в чат из списка `write` фото, видео, аудио, голосовое и документы, по одному или альбомом, с подписью; читать файлы можно только из корней, которые человек вписал в `access.json`; всё остальное отклоняется до обращения к Telegram.

## Problem and contract

Тип плана: product (новая команда записи и новая граница доступа к файловой системе).

- Решения владельца (2026-11-14): корни файлов в `access.json`, список `files`; отдельная команда `message send-media`; тип вложения всегда явный `--as`; загрузка синхронная, потолок 100 МиБ на файл.
- Команда: `tg message send-media <чат> --as photo|video|audio|voice|document --file ПУТЬ [--file ПУТЬ ...] [--caption ТЕКСТ] [--reply-to N] [--topic N] [--silent] [--dry-run]`.
  - `--as` обязателен, без него код 2. Тип никогда не угадывается по расширению; содержимое проверяется на соответствие выбранному типу (по первым байтам), несоответствие даёт код 2 с подсказкой `--as document`.
  - Один `--file` уходит одним сообщением, от двух до десяти (`photo`, `video`, `audio`, `document`) уходят альбомом; для `voice` только один файл (больше: код 2). Подпись уходит с первым вложением альбома.
  - Подпись `--caption` не длиннее 1024 символов (уточняется шагом 1), пустая допустима.
  - Путь может быть относительным: CLI превращает его в абсолютный по своему рабочему каталогу и передаёт Daemon, потому что файл открывает Daemon.
  - `--dry-run` проверяет чат, `write`, корни, тип, размер и подпись и возвращает, что было бы отправлено (число файлов, размеры, тип), без загрузки.
  - Класс безопасности «запись в аккаунт», `dangerous` нет, `--yes` не нужен (как у `message send`). Повторов нет, FLOOD_WAIT возвращается кодом 6 с секундами (решение о записи).
- Ответ: всегда `chat_id` и список `{id, date}`, даже для одного файла (решение после аудита).
- Корни (6.2): ключ `files` в `access.json` рядом с `allow`, `block`, `write`: массив абсолютных путей каталогов; правит только человек. Отсутствие ключа или пустой список значит, что отправка файлов выключена (код 9 `write_disabled` с пояснением, как у `write`). Проверка пути в Daemon: путь очищается и проверяется на вхождение в корень лексически до обращения к файловой системе; затем `EvalSymlinks` и повторная проверка вхождения (симлинк внутри корня, ведущий наружу, отклоняется); файл должен быть обычным (не каталог, не устройство, не FIFO), размером от 1 байта до 100 МиБ; файл открывается один раз и загружается через этот же дескриптор (без повторного открытия по пути). Путь вне корней, несуществующий корень и симлинк наружу дают один и тот же ответ (код 2: `file is outside the allowed roots`), чтобы по ответам нельзя было выяснять, что лежит вне корней; несуществующий файл внутри корня даёт отдельный `file not found` (код 7).
- Размер и время: потолок 100 МиБ на файл и на альбом в сумме не больше 100 МиБ; превышение код 2 до чтения файла. Дедлайн запроса для этого метода фиксированный 600 секунд на сервере и в CLI (вместо роста с размером: проще и покрывает 100 МиБ при скорости от 0,2 МиБ/с), остальные методы остаются на 120 секундах.
- Дроссель: части файла идут через общий дроссель, число одновременных частей ограничено так, чтобы обычные команды не голодали (решает шаг 1).
- Журнал Daemon пишет метод и код итога, путей и подписей в нём нет (как сейчас параметры не пишутся).
- Релиз одним слоем; откат: откат ветки; `access.json` без ключа `files` продолжает работать как раньше.

## Main invariant

1. Без явного `--as`, без записи в чат (`write`) и без корня в `files` ни один байт файла не читается и ни один запрос в Telegram не уходит.
2. Ни один файл вне корней `files` не открывается; симлинки, `..`, относительные пути и несуществующие корни не обходят проверку; ответы об отказе не раскрывают, что лежит вне корней.
3. Агент не может изменить корни: `access.json` правит только человек (проверка прав и перечитывание как у `write`).
4. Файл открывается один раз; проверенный дескриптор это тот, что загружается.
5. Повторов записи нет; сбой загрузки не оставляет частично отправленный альбом без явного ответа об этом.
6. Существующие команды и их ответы не меняются; `message send` по-прежнему текстовая.
7. `internal/cli` не импортирует `tgclient`, gotd, `store`.
8. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram и не читают файлы вне временных каталогов; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: обход корней через симлинк, `..`, гонку подмены файла после проверки. Стратегия: двойная проверка (лексическая и после `EvalSymlinks`), открытие один раз и проверка дескриптора, тесты с симлинками и подменой.
- Риск: агент читает чужой файл, подставив путь, и отправляет его в чат. Стратегия: корни только в `access.json`, отказ по умолчанию, `write` для чата, `--dry-run`.
- Риск: фото и видео без метаданных отправляются как неверный тип. Стратегия: явный `--as`, проверка содержимого, подсказка `--as document`; для видео без метаданных поведение выясняет шаг 1.
- Риск: загрузка 100 МиБ занимает общий затвор и тормозит остальные команды. Стратегия: ограничение числа частей, замер в шаге 1, документированный потолок.
- Риск: обрыв посреди альбома. Стратегия: альбом отправляется одним запросом после загрузки всех файлов; при обрыве загрузки ничего не отправлено, при ошибке самой отправки ответ явный.
- Риск: утечка пути или подписи в журнал или ответ ошибки. Стратегия: журнал без параметров, тесты на отсутствие пути и подписи в журнале и в тексте ошибок, кроме пути, который агент сам передал в этом вызове.

## Known facts

- Аудит шага 1 (Codex, 2026-11-14, отчёт `var/agents/plans/20261114_1907_send_media/audit.md`, в git не входит):
  - gotd: `uploader.NewUploader(api).WithThreads(n).FromFile(ctx, f)` загружает открытый дескриптор и не закрывает его (`FromPath` открыл бы путь повторно); до 10 МиБ части идут последовательными `upload.saveFilePart`, свыше большим режимом; часть по умолчанию 128 КиБ (максимум 512 КиБ), для 100 МиБ около 800 частей. `Media` вызывает `messages.sendMedia`; `Album` делает `messages.uploadMedia` на каждый файл и один `messages.sendMultiMedia`: сбой подготовки не создаёт сообщений, но потерянный ответ при отправке оставляет итог неопределённым.
  - `Video` оставляет длительность и размеры нулями, пока не вызваны `Duration` и `Resolution`; `Voice` задаёт `audio/ogg` и флаг голосового, длительность и волну надо задавать отдельно. Длину подписи gotd не проверяет, предел 1024 принят как проектное ограничение (точный `caption_length_max` аккаунта не известен).
  - Содержимое: `http.DetectContentType` различает JPEG/PNG, но Vorbis и Opus не различает; для Opus нужен `OpusHead` в первой странице Ogg.
  - `access.json`: `allow`, `block`, `write` строго разбираются, любая ошибка закрывает всё; права файла без записи для группы и остальных; перечитывание при изменении; `files` добавляется в `Policy` отдельно от `Allowed` и `Enabled`, чтобы чтение не менялось; внутренний срез корней не отдаётся без копии.
  - Дедлайн 120 секунд стоит у сервера (`Server.call`) и у CLI (`internal/cli/cli.go`, `client.go`); нужны два изменения. Части загрузки идут в общий бакет (18/с, burst 5, два вызова одновременно).
  - Находка: `writeRequest` не содержит `MessagesSendMediaRequest` и `MessagesSendMultiMediaRequest`, хотя `classifyRequest` их знает: без правки middleware повторил бы запись на FLOOD_WAIT.
  - Сохраняет отправленное Daemon после успешного ответа (подпись и признак медиа, бинарного файла в базе нет); пересылка отдаёт `ForwardResult{chat_id, messages:[{id,date}]}`.
  - `just check` в песочнице Codex падает на сокетах (ограничение среды).

- Список `write` и проверка записи уже есть (`internal/access`, `internal/daemon/write.go`); `access.json` перечитывается по времени изменения и размеру, ошибка разбора закрывает всё.
