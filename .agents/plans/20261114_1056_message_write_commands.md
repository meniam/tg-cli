## Goal

Агент отправляет, правит, удаляет и пересылает сообщения командами `tg`, но запись выключена, пока человек не разрешил её для чата в `access.json`; каждое удаление попадает в журнал; любая опасная команда умеет `--dry-run`.

## Problem and contract

Тип плана: product (новое поведение, запись в аккаунт).

- Проблема. Утилита только читает. Запись нужна агенту, но каждая ошибка видна людям и может нарушить условия Telegram (флуд, бан).
- Разрешение записи. В `access.json` добавляется список `write` (идентификаторы чатов, как в `allow`). Запись в чат разрешена, только если он в `write`, виден по правилам чтения и не в `block`. Нет файла или нет списка: запись выключена везде. Файл правит только человек (ограничение про агента того же пользователя то же, что у плана списков). Отказ: код выхода 9 `write_disabled` с подсказкой добавить чат в `write` (чат агенту виден, поэтому подсказка ничего не раскрывает); закрытый чат даёт прежний `not_found`.
- Команды (раздел `message`):
  - `message send <чат> [--text ТЕКСТ | текст из stdin] [--reply-to ID] [--topic ID] [--silent] [--dry-run]`;
  - `message edit <чат> <id> [--text ТЕКСТ | stdin] [--dry-run]`;
  - `message delete <чат> <id>... (--revoke | --for-me) [--yes] [--dry-run]`;
  - `message forward <из чата> <в чат> <id>... [--silent] [--dry-run]`.
  Текст ограничен 4096 символами (проверка до обращения к Telegram, код 2). Форматирование Markdown и HTML (5.4) вне плана: текст уходит как есть.
- Подтверждение и пробный запуск (9.1). `--dry-run` печатает, что будет сделано (чат, тип действия, число сообщений, длину текста, без текста), и ничего не меняет и не вызывает Telegram записи. Удаление и правка требуют `--yes`; без него команда ведёт себя как `--dry-run` и завершается кодом 2 с подсказкой. Отправка и пересылка `--yes` не требуют.
- Повторы. Запись не повторяется автоматически (ни при FLOOD_WAIT, ни при сетевой ошибке): при FLOOD_WAIT код 6, агент решает сам. Идентификатор запроса `random_id` создаёт gotd.
- Журнал удалений (9.3). Файл `deletions.jsonl` в каталоге профиля, права 0600, одна строка JSON на попытку удаления: время, идентификатор аккаунта, инструмент (`tg`), `chat_id`, идентификаторы сообщений, `revoke`, итог (`ok` или код ошибки); текста нет. Запись делается до вызова Telegram (намерение) и после (итог), чтобы упавший процесс оставил след.
- Ответ записи. Команды возвращают `{chat_id, id, date}` (для пересылки список). Отправленные и изменённые сообщения сохраняются в локальную базу (`out: true`), удалённые получают `deleted_at`.
- Дроссель. Запись идёт через существующие классы дросселя: отправка и пересылка в корзины отправки, правка и удаление в общий бакет.
- Релиз одним слоем; откат: откат ветки; журнал `deletions.jsonl` остаётся.

## Main invariant

1. Без `access.json` и без списка `write` ни одна команда записи не доходит до Telegram.
2. Закрытый чат для записи невидим так же, как для чтения (`not_found`, тот же ответ).
3. `--dry-run` не вызывает Telegram записи и не пишет в базу и журнал удалений.
4. Каждая попытка удаления оставляет запись в `deletions.jsonl` до вызова Telegram, без текста сообщений.
5. Запись никогда не повторяется автоматически.
6. Ни тест, ни проверка по умолчанию не пишут в живой Telegram.
7. `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: агент того же пользователя правит `write` в `access.json`. Стратегия: записать в документы; сильнее защита вне плана.
- Риск: запись в живой аккаунт нарушает условия Telegram. Стратегия: дроссель, без повторов, живая проверка только в «Браин Тест» несколькими короткими сообщениями с паузами.
- Риск: отправка и тихая отправка различаются построителями gotd. Стратегия: Step 1 проверяет по исходникам, тесты на поддельном Invoker.
- Риск: пересылка из закрытого чата. Стратегия: оба чата проходят проверку чтения и записи (источник читается, цель пишется).
- Риск: журнал удалений растёт. Стратегия: растёт на одну строку на удаление; ротации нет (вне плана).

## Known facts

- Утилита сейчас только читает; записи в Telegram нет.
- `internal/access` умеет `allow` и `block`; расширять его списком `write`.

- Аудит gotd v0.166.0 (шаг 3): `message.Sender` (`telegram/message/sender.go:25`), `To` строит запрос на `InputPeer` (`peer.go:55`), `Silent` (`builder.go:63`), ответ (`builder.go:81`), `Edit` (`edit.go:36,100`), `ForwardIDs(...).Send` (`forward.go:33,59`), `Delete` (`delete.go:27,53`). У `InputReplyToMessage` есть `TopMsgID`, но построитель его не задаёт: ответ внутри темы идёт прямым `messages.sendMessage` с собственным `random_id` (`tg/tl_input_reply_to_gen.go:46,53,533`). Для канала gotd выбирает только `channels.deleteMessages`, то есть удаление без `revoke` для канала отклоняется до Telegram.
- Находка, влияющая на защиту: `messages.deleteMessages` для личных чатов и обычных групп не принимает `peer`, только идентификаторы сообщений (они уникальны на аккаунт). Поэтому проверка чата по ссылке не исключает удаление сообщения другого чата. Решение плана: перед удалением Daemon проверяет по локальной базе, что все идентификаторы принадлежат выбранному чату, и при неопределённости отказывает.
- Запись исключена из автоповтора после FLOOD_WAIT (дроссель повторяет только запросы чтения).
