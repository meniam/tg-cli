## Goal

Демон с включённым `[background_sync]` сам, медленно и в рабочие часы, догружает историю не полностью загруженных чатов до первого сообщения. В базе у каждого чата видно, загружен ли он полностью, и дата его первого сообщения.

## Problem and contract

Тип плана: product (меняется поведение демона, контракт `chat sync`, модель данных).

**Модель данных.** Миграция `0010_first_message_date.sql`: колонка `sync_state.first_message_date INTEGER` (unix-время первого сообщения чата, пусто, пока загрузка не дошла до начала). Записывается в той же транзакции, что и `complete = 1` (в `SaveHistoryPage`, на пустой странице): значение `MIN(date)` из сохранённых сообщений чата без учёта `deleted_at`. Не вычисляется заново, переживает локальное удаление сообщения. Для 4 чатов, уже имеющих `complete = 1`, значение заполняет миграция из `messages`.

**Планировщик** (`internal/daemon/background_sync.go`, одна горутина, останавливается с демоном):
1. Работает, только если `background_sync.enabled = true` и демон авторизован (`auth_lost` или не готовый клиент пропускают шаг).
2. Окно: с 08:00 до 20:00 по местному времени машины демона (границы настраиваются). Вне окна планировщик спит до 08:00.
3. Интервал между запусками случайный, от 40 до 180 минут, считается от конца предыдущей загрузки (или от старта демона, если загрузок ещё не было). Запуск, выпавший за 20:00, переносится на 08:00.
4. На запуске: если снимок папок старше 4 часов, обновить его (метод `folder.list` без вывода, один запрос); выбрать чат (см. ниже); поставить задачу `d.sync.start` с признаком `source = background` и случайной паузой 2-8 секунд между страницами; в 20:00 отменить задачу через `cancelJob`. Прогресс сохранён по страницам, на следующий день выбор идёт заново, тот же чат не гарантирован.
5. Выбор чата: `complete = 0` (нет строки в `sync_state` или `complete = 0`), доступен по спискам доступа (фильтр внутри запроса), в порядке групп: тип `user`; затем чаты из `folder_chats` с `kind IN ('pinned','include')`, не из групп выше; затем остальные (включая боты). Порядок внутри группы фиксирует Q1. Чаты, чья загрузка завершилась ошибкой, пропускаются до следующего дня (Q2).
6. Ручной `chat sync start` имеет приоритет: если идёт задача планировщика, она отменяется, ручная идёт сразу; планировщик не стартует, пока `hasActive()`.

**Видимость планировщика.** Ответ `daemon status` получает блок `background_sync`: `enabled`, `window` (`start`, `end`), `state` (`disabled`, `waiting_window`, `waiting_interval`, `running`), `next_run_at` (unix-время, пусто при `disabled` и `running`), `last_run_at`, `last_result` (`done`, `cancelled`, `failed`, `skipped`), `current_chat_id`. Время следующего запуска хранится в памяти планировщика.

**`tg status`: дашборд для человека.** Новая команда верхнего уровня, только чтение, всегда читаемый текст, без JSON (флаги `--format json|jsonl|toon` дают код 2 с пояснением, `--human` допустим и ничего не меняет). Данные собирает один новый метод демона `dashboard`, команда только печатает. Блок «Дроссель» берёт остаток `FLOOD_WAIT` аккаунта и число запросов, ждущих в очереди; блок «События» берёт число событий потока за последний час и общее число в базе. Набросок вывода:

Без запущенного демона команда печатает «демон не запущен» и подсказку `just install` или `tg daemon start`, код выхода 3. Название и текст чата в выводе помечаются как недоверенные (`untrusted`) и проходят через тот же вывод, что и `--human` у остальных команд.

**Контракт `chat sync`.** В `rpc.HistorySyncJob` добавляется поле `source` (`manual` или `background`); `chat sync status` показывает его. Остальное прежнее. FEATURES 10.12.1 и 10.12.2 («глубже только по явной команде») меняются: оговорка про планировщик при `enabled = true`.

**Конфиг.** `config.toml`:

```toml
[background_sync]
enabled = false          # по умолчанию выключено
window_start = "08:00"
window_end = "20:00"
interval_min = "40m"
interval_max = "3h"
page_pause_min = "2s"
page_pause_max = "8s"
```

Неверное значение даёт код выхода 2 до запуска демона. Настройки доходят до процесса демона так же, как `behavior.*` (`throttle_config.go`), переменные `TG_CLI_BACKGROUND_SYNC_*`; добавляются в `schema_cmd.go`, `docs/cli/overview.md`, `docs/cli/config.md`, `README.md`.

## Scope

## Main invariant

Без `[background_sync] enabled = true` демон не делает ни одного нового запроса к Telegram: поведение `chat sync` (пауза 2 с, FIFO, возобновление с `oldest_id`), права записи и фильтр доступа не меняются. Планировщик только читает, не пишет в Telegram, не обходит списки доступа и идёт через общий дроссель аккаунта с фоновой меткой.

## Risks and strategy

- Риск: блокировка или `FLOOD_WAIT` от Telegram при долгом обходе. Решение: один рабочий, дроссель (60% ориентира, не больше 2 запросов одновременно), паузы 2-8 с, окно 12 часов, один чат за запуск, выключено по умолчанию. Живую проверку по правилу владельца не проводим; включает владелец сам и следит за `throttled_ms` и `flood_wait`.
- Риск: миграция 0010 необратима для старых бинарников. Решение: копия `~/.config/tg-cli/db/default` перед деплоем (шаг деплоя), как для 0009.
- Риск: ручная загрузка ждёт задачу планировщика. Решение: отмена задачи планировщика при ручном старте (решение владельца).
- Риск: рост базы (повторное чтение сообщений перезаписывает `raw`, оценка из решения `20261118_1211`). Решение: принято владельцем, обход идёт медленно, рост растянут.
- Риск: гонка отмены в 20:00 и завершения задачи. Решение: `cancelJob` уже безопасен для завершённой задачи (`task.State` проверяется под мьютексом); тест на гонку под `-race`.
