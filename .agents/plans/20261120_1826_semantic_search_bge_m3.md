## Goal

Поиск по переписке понимает формы слов (`доставка`, `доставки`, `доставку` дают одни и те же сообщения) и смысл: `tg search --semantic "<запрос>"` находит фрагменты переписки по смыслу и по словам (слияние через RRF трёх ног: точный FTS5, FTS5 со стеммингом и векторы), ограниченные открытыми чатами. После сборки скорость каждой ноги и всего поиска измерена и записана. Индекс строит демон в фоне из локальных сообщений через Ollama и `bge-m3`. Без включения ничего не меняется, без Ollama поиск остаётся обычным.

## Problem and contract

Тип плана: product.

**Лексический уровень (стемминг).** Пакет `internal/stem` приводит слова к основам Snowball (русский и английский, `kljensen/snowball`); слова с цифрами, имена и прочие токены остаются как есть. Основы считаются при индексации и при разборе запроса одной и той же функцией. Миграция `0011_stem_fts.sql` в `store.db` добавляет столбец `messages.stem_text` и таблицу `messages_stem_fts` (FTS5, внешний контент, токенизатор `unicode61`, как у `messages_fts`). Основы пишет скалярная функция `tg_stem()`, зарегистрированная в драйвере `modernc.org/sqlite` на каждом соединении и вызываемая из триггеров вставки и правки; та же функция заполняет `stem_text` у уже сохранённых сообщений при миграции. Точная нога `messages_fts` остаётся: она ловит числа, артикулы и имена так, как написаны. Миграция необратима для старых бинарников, перед деплоем нужна копия базы. Ограничение: внешний инструмент (`sqlite3`), который пишет в базу, упадёт на триггере без функции; пишет в базу только демон. Простая альтернатива без триггеров (основы пишет Go-код в местах записи сообщений) оценивается в Step 1.

**Хранение векторов.** Отдельный файл `vectors.db` в каталоге профиля (`~/.config/tg-cli/db/<профиль>/`), SQLite на `modernc.org/sqlite`, своя версия схемы (`PRAGMA user_version`), миграции независимы от `store.db`. Таблица `fragments`: `chat_id`, `topic_id` (0, если тем нет), `first_id`, `last_id` (ключ `(chat_id, first_id)`), `starts_at`, `ends_at`, `chars`, `text_hash`, `model`, `dim`, `vec BLOB` (float32, нормализован), `embedded_at`. Текста сообщений в `vectors.db` нет. Полностью производный файл: можно удалить, индекс построится заново.

**Поиск векторов.** Полный перебор в Go по векторам, загруженным в память (около 26 МБ на сегодняшней базе). Фильтр по открытым чатам применяется до подсчёта. Интерфейс `vectorIndex` с одной реализацией, чтобы позже можно было заменить (`sqlite-vec`, zvec), если объём вырастет.

**Нарезка** (стартовые значения из `brain-agent`, константы в коде с комментарием о происхождении): фрагмент это непрерывный отрезок одного чата; разрез при паузе 30 минут, если набрано 300 символов; потолок 1500 символов с перекрытием 200 при разрезе по потолку; ответ (`reply_to`) на сообщение из буфера отменяет разрез по паузе; недобранный фрагмент закрывается тишиной 24 часа; предельная длительность 7 суток; сообщение длиннее потолка не режется; в индекс идут фрагменты от 200 символов, короткие остаются только в FTS; открытый фрагмент пересчитывается при приросте на 300 символов. Разрез также при смене темы форума (`topic_id`): фрагмент не смешивает темы. Вставка текста цитаты вне объёма первой версии.

**Эмбеддер.** Ollama по HTTP (`/api/embed`, пачки, `num_ctx` 8192), модель `bge-m3` без префиксов. Адрес по умолчанию `http://127.0.0.1:11434`. Веса лежат в хранилище Ollama, в бинарнике кода только клиент. Имя модели и дайджест пишутся в строку: смена модели помечает индекс устаревшим и запускает пересборку, смешивать векторы разных моделей нельзя.

**Индексатор (демон).** Один рабочий, только при `[semantic_search] enabled = true`. Инкрементально по `text_hash` и `embedded_at`; запускается через 10 минут после старта и далее каждые 10 минут, после окончания фоновой загрузки истории и по команде `tg search index start`. Закрытые чаты не индексируются, векторы закрытых и удалённых чатов и фрагментов убирает фоновая сверка. Если Ollama недоступен или модели нет, задача пишет причину в статус и повторит позже; Telegram не вызывается вообще.

**Команда.** Обычный `tg search` по области `messages` получает вторую ногу со стеммингом и сливает точную и стеммированную выдачи через RRF (форма ответа прежняя, решение по умолчанию в Q4). `tg search --semantic <запрос>`: три ноги, точный FTS5 и FTS5 со стеммингом по `messages` и вектор по `fragments`; слияние RRF `k = 60`, ранг фрагмента равен лучшему рангу его сообщений. Ответ: фрагменты (`chat_id`, `first_id`, `last_id`, `starts_at`, `ends_at`, `score`, `sources`, `text` из `messages` до 1500 символов с пометкой `untrusted`). Эмбеддинг запроса считает Ollama в момент вызова. Если вектор недоступен, ответ строится по FTS и несёт `vector_skipped` с причиной. Новые команды: `tg search index start|status|cancel`. Конфиг: секция `[semantic_search]` (`enabled`, `ollama_url`, `model`, `batch`, `interval`) и переменные `TG_CLI_SEMANTIC_SEARCH_*`.

**Ссылки на сообщения.** Каждый результат поиска несёт кликабельные ссылки на сообщения по правилам Telegram, построенные локально без запроса к Telegram функцией `chatref.FormatMessageLink` из `chats.type`, `chats.username` и `topic_id` сообщения:
- фрагмент (`--semantic`): `link` ведёт на первое сообщение фрагмента (начало диалога, `first_id`) и `match_link` на сообщение, лучше всего совпавшее с запросом (если оно известно); текст фрагмента идёт рядом;
- обычный `tg search` по `messages`: у каждого попадания поле `link` на это сообщение (добавление поля, форма ответа прежняя);
- публичный чат с именем: `https://t.me/<username>/<id>`; приватный канал или супергруппа: `https://t.me/c/<id>/<id>`; сообщение в теме форума: `https://t.me/c/<id>/<тема>/<id>` (или с именем); личный чат и обычная группа: веб-ссылки нет, поле `link` равно `null`, рядом `link_unavailable` с причиной (`private_chat` или `basic_group`), поиск не падает (вопрос о нативной ссылке в Q5);
- ссылка называет только чат и номер, текста сообщений не содержит.

**Статус.** Блок `semantic_search` в `daemon status` и строка `Semantic` в `tg status`: включено ли, модель, проиндексировано фрагментов из возможных, состояние задачи, причина простоя.

## Main invariant

Без `[semantic_search] enabled = true` ни одного запроса к Ollama, `vectors.db` не создаётся. Форма ответа `tg search` не меняется, точный FTS остаётся одной из ног. Включённый индексатор только читает `store.db`, пишет только в `vectors.db`, к Telegram не обращается. Закрытые `access.json` чаты не попадают ни в индекс, ни в выдачу. Тексты сообщений не копируются в `vectors.db`. Любой сбой вектора оставляет обычный поиск рабочим.

## Risks and strategy

- Риск: пороги нарезки подобраны на другом корпусе. Решение: симуляция на этой базе (сделана, 98,9% покрытия), эталонный набор вопросов (Step 9), пересмотр порогов по нему.
- Риск: стемминг даёт ложные совпадения (разные слова с одной основой). Решение: точная нога остаётся и участвует в RRF; на эталонном наборе (Step 10) сравнивается выдача с и без основы.
- Риск: миграция `0011` необратима и трогает 55 тысяч строк. Решение: копия базы, тест миграции с версии 10, время работы замерено в Step 3.
- Риск: переписка уходит наружу. Решение: только Ollama на `127.0.0.1`; шаг проверки, что сервис не слушает внешние адреса; внешних API в плане нет.
- Риск: индексация грузит процессор и GPU. Решение: один рабочий, пачки по 16, пауза между пачками; первая пересборка около 5 минут (замер спайка), дальше инкременты.
- Риск: смена модели Ollama без пересборки даёт несравнимые векторы. Решение: имя и дайджест в каждой строке, несовпадение даёт статус «устарел».
- Риск: рассинхрон индекса и сообщений (правка, удаление, закрытие чата). Решение: `text_hash`, сверка, тесты на каждый случай.
- Риск: `Ollama` не запущен. Решение: деградация до FTS с `vector_skipped`, статус с причиной.
