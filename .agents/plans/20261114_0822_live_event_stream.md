## Goal

Агент видит новые сообщения и другие события по мере поступления командой `message watch`, не теряет события между сессиями и после разрыва связи, а Daemon не выдаёт события закрытых чатов.

## Problem and contract

Тип плана: product (новое поведение, новая таблица, новый метод Daemon).

- Проблема. Сейчас агент узнаёт о новых сообщениях только опросом `message history`: это нагружает аккаунт, шумит в дросселе и теряет события, пока агент не смотрит.
- Источник. Daemon запускает менеджер обновлений gotd (`updates.Manager`) после входа в аккаунт и держит его, пока работает. Менеджер сам догоняет пропущенное после разрыва (`getDifference`). Состояние менеджера (`pts`, `qts`, `date`, `seq`, pts каналов) хранится в `account_state` и переживает перезапуск Daemon.
- События. Типы: `message.new`, `message.edit`, `message.delete`, `reaction`, `read`, `typing`, `status`, `gap` (менеджер не смог восстановить пропуск), `lagged` (подписчик не успевает, см. ниже). Каждое событие несёт `type`, `chat_id` (если есть), время и данные по типу; поля с чужим текстом помечены `untrusted` в `schema`.
- Журнал событий. События `message.*` и `reaction` сохраняются в новой таблице `events` (возрастающий `id`, тип, `chat_id`, время, JSON без служебного шума). `typing`, `read` и `status` живые: только подписанным, не сохраняются и не воспроизводятся. Сообщения и правки пишутся и в `messages` (правка сохраняет прежнюю версию в `message_versions`, удаление ставит `deleted_at`), поэтому локальный поиск видит поток.
- Курсор. Курсор события это его `id` в `events`, строкой. Агент продолжает с `--after <cursor>`: Daemon сначала отдаёт сохранённые события после курсора, затем живые, без разрыва и без повторов. Курсор содержит и состояние менеджера (`pts`, `qts`, `date`) для сверки с пунктом 8.3.1 (формат в открытых вопросах). Хранение: 7 суток или 100 000 событий, что наступит раньше; курсор старше границы даёт ошибку `cursor_expired`.
- Метод `subscribe`. Запрос `subscribe` с параметрами: `chats` (ссылки, по умолчанию все разрешённые), `topic`, `types`, `after`. Ответ: `subscription_id` и стартовый курсор. Дальше Daemon шлёт уведомления без `id` (метод `event`, 2.4.1) на то же соединение. Подписка заканчивается закрытием сокета (2.6) или методом `unsubscribe`. Одно соединение: одна подписка.
- Медленный подписчик. Очередь подписчика ограничена (1000 событий). При переполнении Daemon шлёт событие `lagged` с курсором последнего доставленного и закрывает подписку: события не теряются, они лежат в журнале, агент продолжает с курсора.
- Фильтр чатов. События закрытых чатов (`access.json`, см. план списков) отбрасываются до записи в `events` и до доставки; `typing`, `read` и `status` по ним тоже. Режим закрытия берётся из политики на момент события.
- CLI. `message watch [--chat <ссылка>]... [--topic N] [--types a,b] [--after <cursor>]`: печатает события по одному в строке `jsonl` (по умолчанию формат `jsonl`, `--format json` допустим только с `--max-events`), завершается по Ctrl-C (код 0), по закрытию подписки Daemon'ом (код 1 для `lagged`, подсказка `--after`), без Daemon код 3. Класс безопасности «чтение»; результат описан в `schema`. Поток работает только через Daemon (8.1.2).
- Дроссель. Запросы менеджера идут через `c.tg.API()` и под дросселем; пауза FLOOD_WAIT откладывает догоняющие запросы, события не теряются, потому что состояние менеджера не продвигается без обработки.
- Релиз. Одним слоем; откат: откат ветки (таблица `events` остаётся и игнорируется).

## Main invariant

1. Событие закрытого чата не попадает ни в `events`, ни в уведомление подписчику.
2. Курсор не теряет и не повторяет события: от сохранённого курсора агент получает каждое сохранённое событие ровно один раз, затем живые.
3. Состояние менеджера продвигается только после записи события в `events` (событие записывается, потом обновляется курсор менеджера; при сбое событие приходит повторно и обработчик идемпотентен по ключу `(chat_id, message_id, type, версия)`).
4. Без подписчиков Daemon не увеличивает нагрузку сверх менеджера, и дроссель покрывает его запросы.
5. `internal/cli` не импортирует `tgclient`, gotd и `store`.
6. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram.
7. `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: менеджер gotd при первом запуске без состояния продолжает «с этого момента» и не догружает историю. Стратегия: принять (цель потока это новое), записать в документ; глубокая загрузка отдельный план.
- Риск: `ChannelDifferenceTooLong` и недоступные каналы оставляют пропуск. Стратегия: событие `gap` с `chat_id`, агент сам читает историю командой `message history`.
- Риск: запись события и сдвиг состояния не атомарны. Стратегия: порядок «событие, потом состояние», идемпотентная запись по естественному ключу.
- Риск: рост таблицы `events` и `messages`. Стратегия: ограничение хранения (7 суток или 100 000), очистка при старте и раз в час; пересмотреть по замеру на живой проверке.
- Риск: медленный подписчик тормозит Daemon. Стратегия: ограниченная очередь и `lagged`, доставка не блокирует обработку обновлений.
- Риск: фильтр чатов пропускает событие без `chat_id` (например `status`). Стратегия: события без чата не несут чужого текста; тест на каждый тип.
- Риск: менеджер держит соединения и запросы, пока Daemon простаивает; режим `--idle-timeout` остановит Daemon по простою. Стратегия: подписчик считается активностью, активный менеджер сам по себе нет; записать в документ.

## Known facts

- `rpc.Request` без `ID` это уведомление, `rpc.Client.Notify` отправляет такие запросы; доставки уведомлений от Daemon клиенту пока нет.
- У gotd `updates.Manager` принимает `StateStorage` (pts, qts, date, seq, pts каналов) и `ChannelAccessHasher` (подходит `peers.Manager`); без хранилища состояние в памяти.
- Таблица `account_state(key, value JSON)` в `store` есть и не используется.
- Проект не вызывает `updates`.
- Аудит gotd v0.166.0 (2026-11-14): `updates.New(Config)` возвращает `*Manager`, который сам реализует `telegram.UpdateHandler` (`Handle(ctx, tg.UpdatesClass)`, `telegram/client.go:32`); его подключают как `telegram.Options.UpdateHandler`, а `Manager.Run(ctx, api, userID, AuthOptions{Forget, OnStart})` вызывают после входа (`updates/manager.go:165`); `api` это три метода `UpdatesGetState|GetDifference|GetChannelDifference` (`updates/config.go:18-22`), их даёт `c.tg.API()`, поэтому они идут через Middlewares и под дроссель. Без сохранённого состояния `Run` берёт состояние с сервера (поэтому первый запуск идёт «с этого момента»), обратный вызов `OnLoadUserStateFailed` сообщает об этом. Хешам доступа подходит `*peers.Manager` (`AccessHasher`).
- Обновления для событий: `UpdateNewMessage`, `UpdateNewChannelMessage`, `UpdateEditMessage`, `UpdateEditChannelMessage`, `UpdateDeleteMessages`, `UpdateDeleteChannelMessages`, `UpdateMessageReactions` (есть `Peer`), `UpdateReadHistoryInbox|Outbox`, `UpdateReadChannelInbox|Outbox`, `UpdateUserTyping`, `UpdateChatUserTyping`, `UpdateChannelUserTyping`, `UpdateUserStatus` (`tg/tl_update_gen.go`).
- Находка, влияющая на фильтр чатов: `UpdateDeleteMessages` (личные чаты и обычные группы) несёт только список `Messages []int` без идентификатора чата (`tg/tl_update_gen.go:404`), у `UpdateDeleteChannelMessages` есть `ChannelID`. Идентификатор чата для удаления в личном чате или обычной группе можно узнать только по локальной базе (идентификатор сообщения в них уникален на аккаунт). Решение плана: если фильтр чатов включён и чат удаления определить нельзя, событие отбрасывается (закрыто по умолчанию); без фильтра событие идёт с пустым `chat_id`.
