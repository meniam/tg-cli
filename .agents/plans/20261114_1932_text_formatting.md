## Goal

Агент отправляет и правит сообщения с любым поддерживаемым форматированием: обычные сущности из HTML и из Markdown, явный список сущностей и RichMessage из HTML и из Markdown; прочитанные RichMessage дают осмысленный текст.

## Problem and contract

Тип плана: product (расширение `message send` и `message edit`).

- Решение владельца (2026-11-14): поддержать все типы форматирования, включая RichMessage в HTML и в Markdown.
- Флаги `message send` и `message edit` (взаимоисключающие, без них текст уходит как раньше, простой):
  - `--parse html` и `--parse markdown`: текст разбирается gotd в сущности (классическое форматирование Telegram: жирный, курсив, подчёркнутый, зачёркнутый, спойлер, код, блок кода, цитата, ссылка, упоминание); сообщение уходит обычным `message` с `entities`.
  - `--parse rich-html` и `--parse rich-markdown`: текст уходит как RichMessage (`rich_message` в `messages.sendMessage` и `messages.editMessage`): заголовки, списки, таблицы, формулы, сворачиваемые блоки, спойлеры и остальное по `rich/spec.md`.
  - `--entities ФАЙЛ|-`: явный список сущностей в JSON (тип, смещение и длина в единицах UTF-16 как у Telegram, нужные поля), текст берётся из `--text` или stdin как простой; допустимы типы, перечисленные в разделе «Сущности»; смещения проверяются до обращения к Telegram.
- Сущности по `--entities`: `bold`, `italic`, `underline`, `strikethrough`, `spoiler`, `code`, `pre` (с языком), `blockquote` (с признаком сворачивания), `text_url`, `url`, `email`, `phone`, `mention`, `mention_name` (по id пользователя), `hashtag`, `cashtag`, `bot_command`, `custom_emoji` (по id) и `date_time`, если сервер их принимает (шаг 1 выясняет); неизвестный тип даёт код 2.
- Разбор до отправки: ошибки разбора HTML и Markdown и неверные сущности дают код 2 с понятным текстом и позицией, Telegram не вызывается. `--dry-run` показывает режим, число сущностей или признак RichMessage и длину.
- Длина: простой и классический текст не длиннее 4096 символов после разбора (по тексту без разметки); предел RichMessage уточняет шаг 1 и проба.
- Правка: те же флаги у `message edit`; смена режима при правке разрешена (простой текст можно заменить RichMessage и обратно), если сервер это допускает (шаг 1 и проба).
- Чтение: сообщение, у которого есть `rich_message`, отдаётся в `text` как простой текст блоков (заголовки, абзацы, элементы списков и ячейки таблиц через переводы строк), чтобы агент не получал пустое сообщение; признак RichMessage не меняет остальные поля; в базу сохраняется тот же текст. Сущности и разметка при чтении не отдаются (вне плана).
- Класс безопасности и защита не меняются: запись в аккаунт, нужен `write`, без повторов, `--dry-run`, правка с `--yes`.
- Релиз одним слоем; откат: откат ветки.

## Scope

- В плане: `internal/rpc` (поля параметров), `tgclient` (разбор HTML, Markdown, сущностей, RichMessage; отправка и правка; чтение `rich_message`), Daemon (проверки и `--dry-run`), CLI (флаги `--parse`, `--entities`), схема, тесты, документы, живая проверка в «Браин Тест».
- Вне плана: форматирование подписей к медиа (план отправки медиа `20261114_1907_send_media`), отдача сущностей и разметки при чтении, `message forward` с форматированием, превью ссылок, отправка RichMessage с вложенными файлами и фото (`files` в `inputRichMessage*`), редактор сущностей по шаблонам, MarkdownV2 Bot API как отдельный диалект (берётся Markdown gotd).
- Затрагиваются: `internal/{rpc,tgclient,daemon,cli,schema}`, `AGENTS.md`, `FEATURES.md`, `README.md`, `docs/skill/tg-cli/`, `.agents/decisions/`.

## Main invariant

1. Без флагов формата поведение `message send` и `message edit` не меняется ни байтом (простой текст, те же коды).
2. Ошибка разбора или неверная сущность не доходят до Telegram: код 2, счётчик вызовов подмены равен нулю.
3. Повторов записи нет; режимы форматирования не добавляют повторов.
4. Текст прочитанного RichMessage никогда не пуст, если в блоках есть текст; чужой текст остаётся помеченным `untrusted`.
5. `internal/cli` не импортирует `tgclient`, gotd, `store`.
6. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: пользовательский аккаунт не может отправлять RichMessage или слой клиента старый. Стратегия: ранняя проба на «Браин Тест» (шаг 5) сразу после реализации; если сервер отказывает, режимы `rich-*` остаются в коде, возвращают понятную ошибку Telegram кодом 5, а документы называют это ограничением; остальные режимы работают.
- Риск: сообщение RichMessage приходит в истории пустым или в другом виде. Стратегия: шаг 3 добавляет разбор `rich_message` в текст; проба проверяет отправку, чтение и правку.
- Риск: смещения сущностей считаются в UTF-16, ошибки на эмодзи. Стратегия: тесты на эмодзи и символы вне BMP для `--entities` и для HTML и Markdown.
- Риск: упоминание по id без разрешителя пользователя (`tg://user?id=`). Стратегия: разрешитель из известных людей базы или код 2 с понятным текстом; решает шаг 1.
- Риск: форматирование нельзя проверить глазами из этой сессии. Стратегия: проверка принятия сервером и текста по числам; вид в чате подтверждает владелец по тестовым сообщениям в «Браин Тест», и шаг 6 прямо просит его об этом.

- Аудит шага 1 (Codex, 2026-11-14, отчёт `var/agents/plans/20261114_1932_text_formatting/audit.md`, в git не входит):
  - Смещения сущностей считаются в UTF-16 (`entity.Builder`, `UTF16Len`); `--entities` обязан отвергать границы внутри суррогатной пары. gotd имеет конструкторы всех плановых сущностей; TL-имя даты `MessageEntityFormattedDate`, JSON-имя `date_time` надо отобразить отдельно; принятие её сервером при отправке не подтверждено.
  - HTML: `b/strong`, `i/em`, `u/ins`, `s/strike/del`, `a`, `code`, `pre` (язык из `class=language-X`), `tg-spoiler`, `tg-emoji emoji-id`, `blockquote expandable`, `tg-time`; ошибка разбора ссылки в HTML молча заменяется отсутствием форматтера, поэтому нужен отдельный строгий контроль. Markdown gotd: CommonMark плюс зачёркнутый и `||спойлер||`, код с языком, ссылки, `![x](tg://emoji?id=N)`, цитата; заголовки и списки остаются обычным текстом.
  - Упоминание по id (`tg://user?id=N`) требует разрешителя `InputUser` с access hash; `store.Person` hash не хранит.
  - `rich.HTML` и `rich.Markdown` создают исходник для серверного разбора; локальные `ParseHTML` и `ParseMarkdown` лишь подмножество. `message.Builder.RichMessage` и `EditMessageBuilder.RichMessage` кладут аргумент в `rich_message` запроса.
  - В прочитанном `tg.Message` поле `Message` самостоятельно, дерево доступно через `GetRichMessage()` (флаг `Flags2` бит 13); для чтения нужна своя функция плоского текста (`richMessageText`, `richTextText`: `TextPlain`, `TextConcat`, обёртки, `TextMath.Source`, `TextCustomEmoji.Alt`; блоки через `\n`, список по элементам, таблица строками, ячейки через tab, вложенные блоки рекурсивно); готовая `plainText` в gotd покрывает только `TextPlain` и `TextConcat`.
  - Сообщение в `rpc.Message` строит `internal/tgclient/message.go:17` (не `convert.go`): текст берётся только из `m.Message`; история, `get`, закреплённые, контекст, поиск и события потока вызывают один `toMessage`, поэтому одна правка покрывает всё.
  - Длины: `config` отдаёт `CaptionLengthMax` и `MessageLengthMax` без чисел; отдельного предела RichMessage нет; текущие CLI, Daemon и tgclient жёстко держат 4096 рун (не UTF-16).
  - Daemon после успешных send и edit сохраняет `p.Text` (`internal/daemon/write.go:99,126`): в режимах разбора это исходная разметка, что неверно.
  - `just check` в песочнице Codex падает на сокетах (ограничение среды).

- gotd v0.166.0 содержит `telegram/message/html`, `markdown`, `entity`, `styling`, `rich` и методы `Builder.RichMessage`, `EditMessageBuilder.RichMessage`; слой схемы 233.
- В `tg.Message` есть поле `RichMessage`; `messages.sendMessage` и `messages.editMessage` принимают `rich_message`.
- Спецификация Rich Markdown лежит в `telegram/message/rich/spec.md` (GFM плюс спойлер, выделение, формулы, таблицы, детали, коллажи).
