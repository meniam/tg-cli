## Goal

Агент переносит вход между профилями и машинами строкой сессии и входит в аккаунт без терминала. Строка сессии и пароль 2FA не попадают в argv, логи и ответы, кроме явно запрошенного вывода строки; два процесса на одном ключе на одной машине не запускаются, а потеря ключа видна в `auth status`.

## Problem and contract

Тип плана: product (новые команды, новый способ входа, правка требования 1.1.2).

### Что уже есть (по коду и `tg schema`)

- Фоновый Daemon не получает секреты в argv: ключи приложения идут через окружение и файл профиля (2.12.7, `internal/daemon/launch_unix.go`).
- `auth login --phone` уже принимает номер флагом (`internal/cli/auth_cmd.go`, флаг `phone`).
- Код входа CLI читает через `ReadLine` из stdin без проверки терминала (`internal/cli/terminal.go`), но запрос идёт до того, как код известен, поэтому агенту это не помогает: пустой stdin завершает вход кодом 2 (`readFailed`).
- `auth login --qr` не требует ввода, пока у аккаунта нет 2FA: URL кода печатается в stderr, CLI ждёт `auth.wait` (`internal/cli/auth_cmd.go`, `internal/cli/qr.go`). С 2FA пароль читает `ReadSecret`, который без терминала отказывает.
- Поток входа живёт в Daemon независимо от соединения CLI: `loginManager.begin` строит контекст от `baseCtx` с тайм-аутом 5 минут (`internal/daemon/login.go`), а RPC-шаги `auth.code`, `auth.password`, `auth.wait`, `auth.cancel` уже есть (`internal/rpc/api.go`). Двухшаговый вход требует только команд CLI.
- Сессия лежит в `<profile>/session.json` с правами 0600 в каталоге 0700; формат gotd JSON (`internal/daemon/paths.go`, `internal/tgclient/client.go`).
- Блокировка профиля `daemon.lock` (`flock`) держится всё время работы Daemon (`internal/daemon/lock_unix.go`); второй Daemon того же профиля не стартует (1.6.1).
- Ошибки 401 переводятся в код 4 (`internal/tgclient/errors.go`); `AUTH_KEY_DUPLICATED` (406) отдельно не обрабатывается, `OnAuthLost` gotd не подключён.

### Чего нет

Экспорта и импорта строки (1.3.1, 1.3.2), неинтерактивного входа (1.4.1), чтения пароля без терминала, защиты от двух профилей с одним ключом, сообщения о потерянном ключе.

### Контракт (для рекомендованных вариантов Q1 до Q11; другой ответ меняет отмеченные места)

Вход без терминала (1.4.1, Q1 до Q3):

- `tg auth login --phone <номер> --no-input [--password-file PATH]`: CLI ничего не спрашивает. Без `--phone` и без `--qr` код 2 до Daemon. Команда запускает `auth.start` и, когда Telegram ждёт код, печатает конверт `{"state":"code_required","delivery",...}` и завершается кодом 0. Поток входа остаётся в Daemon до 5 минут с момента старта; `auth status` показывает `login_state: code_required`.
- `tg auth code [--password-file PATH]` (класс `account_write`): читает код одной строкой из stdin; если stdin это терминал, спрашивает подсказкой. Пустой код или строка длиннее 64 символов дают код 2 до Daemon. Код уходит в `auth.code`. Ответ: `authorized` с пользователем или `password_required`. С `--password-file` и ответом `password_required` команда сразу отправляет пароль из файла. Неверный код даёт код 5, как сейчас (1.1.3).
- `tg auth password [--password-file PATH | --password-stdin]` (класс `account_write`): пароль из файла или одной строкой из stdin; без флагов и с терминалом спрашивает без эха, как сейчас; без флагов и без терминала код 2 с подсказкой про оба флага.
- `--no-input` и `--password-file` работают и с `auth login --qr`: QR печатается в stderr, CLI ждёт сканирования, а на 2FA отправляет пароль из файла; без файла и без терминала команда завершается кодом 0 с `state: password_required`, а пароль передаёт `tg auth password`.
- Шаг не в своём состоянии (нет входа, ждём не код) остаётся ошибкой `CodeLoginState` с текущим кодом выхода; нового кода выхода нет.
- `--password-file`: обычный файл (ссылка разрешается, проверяется цель), владелец совпадает с текущим пользователем, права без битов группы и остальных (`mode & 0o077 == 0`), не больше 1 КиБ; иначе код 2 с причиной без содержимого. Пароль это всё содержимое без одного завершающего `\n` или `\r\n`, пробелы сохраняются. Пустой пароль код 2.
- `--password-stdin`: одна строка до 1 КиБ, срезается только перевод строки. `--password-stdin` у `auth code` запрещён (stdin занят кодом), код 2.
- 1.1.2 меняется на: «Код входа и пароль 2FA не попадают в argv, вывод и логи; их вводят интерактивно, через stdin или, для пароля, через файл с правами владельца». Переменная окружения для пароля не принимается (Q2).

Экспорт (1.3.1, Q4, Q5, Q10, Q11):

- `tg session export --out PATH --yes` (класс `read`, `dangerous`): без `--yes` код 2 до чтения сессии. `--out` обязателен: файл создаётся с `O_CREATE|O_EXCL` и правами 0600, существующий файл не перезаписывается (код 2), каталог должен существовать. `--out -` печатает строку в `data.session` конверта; stderr предупреждает, что строка это полный вход в аккаунт.
- Если Daemon профиля работает, CLI берёт строку методом `session.export` (Daemon читает сессию через тот же объект хранилища gotd, под его мьютексом). Если не работает, CLI берёт блокировку профиля `daemon.lock` и читает `session.json` сам, Daemon не запускается. Сессии нет или аккаунт не вошёл: код 4.
- Ответ: `{profile, path?, session?, format: "tgcli1", user_id?, dc, key_id, client?}`; `key_id` это `AuthKeyID` в hex (он идёт открытым в каждом пакете MTProto и секретом не является), `client` это имя пресета профиля, `api_hash` в строку и ответ не входит.
- Формат строки `tgcli1.<base64url без паддинга>` от JSON `{"v":1,"session":<объект session.json gotd>,"user_id","dc","client","api_id","created_at"}`. Строка помещается в один кадр RPC (оценка до 4 КиБ при пяти DC; шаг 1 меряет).

Импорт (1.3.2, Q6 до Q11):

- `tg session import --from PATH|- --yes [--force]` (класс `local_write`, `dangerous`): без `--yes` код 2. Строка читается из файла (те же проверки владельца и прав, что у `--password-file`, предел 64 КиБ) или из stdin при `--from -`; в argv строка не принимается. Пробелы и переводы строк по краям срезаются.
- Принимаются `tgcli1.`, строка Telethon и строка gramjs (`tg` 0.5.1). Неизвестный формат или битая строка: код 2, текст ошибки не содержит ни одного байта строки.
- Импорт идёт без сети и без Daemon: CLI берёт `daemon.lock` профиля; Daemon профиля работает, значит код 2 с подсказкой `tg daemon stop`. Профиль создаётся с каталогом 0700, если его нет.
- Перезапись (Q8): есть `session.json` или `store.db`, значит без `--force` код 2. С `--force` импорт разрешён, только если `UserID` старой и новой сессии известны и совпадают (обновление ключа того же аккаунта); иначе код 2 с советом взять новый профиль. Старый ключ на сервере не выходит из аккаунта: он остаётся в списке устройств, ответ и stderr об этом говорят.
- Запись атомарная: временный файл 0600 в каталоге профиля, `fsync`, `rename` на `session.json`. Имя пресета из строки сохраняется в `<profile>/client`, если файла нет; если пресет профиля другой, stderr предупреждает, файл не меняется.
- Ответ: `{profile, format, user_id?, dc, key_id, replaced, duplicates: [профили с тем же key_id]}`. Проверки входа в Telegram при импорте нет: её делает следующий `daemon start` и `auth status`.

Два процесса на одном ключе (Q9, AGENTS.md Security):

- Копия разрешена. `daemon start` (фоновый и `--foreground`) до подключения ищет в базовом каталоге профилей (`TG_CLI_HOME` или каталог по умолчанию) другие профили с тем же `key_id`; если у такого профиля занята `daemon.lock`, запуск отклоняется кодом 2 с именем профиля. Значение ключа при этом не читается в лог и не сравнивается целиком в выводе.
- Daemon подключает `Options.OnAuthLost` gotd: при потере авторизации (`key_invalid`, `revoked`, `unregistered`, `expired`, `banned`, `deleted`) он запоминает вид потери, `daemon status` и `auth status` показывают поле `auth_lost`, команды аккаунта получают код 4 с текстом «authorization lost: <kind>; log in again». Daemon продолжает работать, `session.json` не удаляется.
- Защита покрывает только профили одного базового каталога на одной машине. Копия строки на другой машине не видна; об этом предупреждают stderr экспорта, справочник и навык.

Общее:

- Журнал Daemon пишет только метод, длительность и код (`session.export` не исключение); `--verbose` не печатает параметры и результат. Ни одна ошибка не содержит строку, код или пароль.
- Миграции нет: схема базы не меняется.
- Релиз одним слоем; откат: откат ветки, профили совместимы (формат `session.json` не меняется).

## Scope

- В плане: `internal/{sessionstr,rpc,tgclient,daemon,cli}`, схема, тесты, справочник, документы, живая проверка по Q12.
- Вне плана: `tg auth logout` и выход старого ключа на сервере при перезаписи; перенос входа без копии ключа через `auth.acceptLoginToken` (профиль A подтверждает QR профиля B, у каждого свой ключ); экспорт в форматы Telethon и gramjs; шифрование строки паролем; переменная окружения со строкой сессии; хранение сессии в связке ключей ОС; защита от копии на другой машине; очистка секретов в памяти процесса (Go этого не гарантирует); импорт TDesktop `tdata`.
- Затрагиваются: файлы из раздела «Файлы потока».

## Main invariant

1. Строка сессии, код и пароль 2FA не попадают в argv ни одного процесса утилиты, в `daemon.log`, `--verbose`, тексты ошибок и ответы; единственное исключение: `session export --out -` печатает строку в `data.session`.
2. Ни один файл с секретом не создаётся с правами шире 0600; существующий файл экспорта не перезаписывается; `session.json` заменяется только атомарно.
3. Импорт не меняет профиль с работающим Daemon и не смешивает аккаунты: чужой `UserID` поверх существующей сессии или базы не ложится.
4. Второй Daemon с тем же `key_id` в том же базовом каталоге не подключается к Telegram.
5. Интерактивный `auth login` без новых флагов ведёт себя как сейчас (1.1.1 до 1.1.6, 1.12).
6. `internal/cli` не импортирует `tgclient`, gotd, `store`; `sessionstr` не импортирует gotd.
7. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: две копии ключа работают одновременно, Telegram отвечает `AUTH_KEY_DUPLICATED` и ключ умирает, владелец входит заново. Стратегия: проверка соседних профилей при старте, `auth_lost` в статусе, `--yes` и предупреждение у экспорта, совет в навыке «одна строка, один работающий процесс». Остаток: копию на другой машине утилита не видит.
- Риск: агент получает строку сессии в свой контекст и журнал своей среды. Стратегия: по умолчанию файл 0600 (`--out PATH`), вывод в stdout только явным `--out -`; навык советует файл.
- Риск: подсунутая через чат строка (prompt injection) переводит профиль на чужой аккаунт. Стратегия: `--yes`, запрет перезаписи чужим `UserID`, `--expect-user` у команд; навык: импортировать только строку, которую дал владелец. Шаг 1 выясняет, нужен ли gotd адрес `Addr` из строки; если нет, импорт оставляет только номер DC, и строка не может направить Daemon на чужой адрес.
- Риск: пароль 2FA в окружении наследуется фоновым Daemon (`cmd.Env = os.Environ()`) и виден `ps eww` тому же пользователю. Стратегия: переменная окружения не принимается (Q2).
- Риск: `session.json` пишется gotd через `os.WriteFile` без атомарной замены; чтение файла при работающем Daemon может застать половину. Стратегия: при работающем Daemon экспорт идёт через RPC под мьютексом хранилища, без Daemon под `daemon.lock`.
- Риск: ключ, созданный под одним `api_id`, работает под другим (импорт строки gramjs в профиль с пресетом `desktop`). Стратегия: строка несёт `client` и `api_id`, импорт предупреждает о расхождении; живое поведение не проверено, пункт в «не проверено» `FEATURES.md`.
- Риск: двухшаговый вход оставляет поток в Daemon, если агент не прислал код. Стратегия: тайм-аут 5 минут уже есть, `auth cancel` сбрасывает; ответ `auth login --no-input` и справочник называют срок.
- Риск: слияние с параллельными потоками. `net_transport` почти наверняка правит `telegram.Options` в `internal/tgclient/client.go`, `daemon_lifecycle` правит `daemon start` и `daemon.go`. Стратегия: вставки отдельными строками; проверка соседних профилей в своём файле `session.go` и одна строка вызова; при конфликте сохраняются обе стороны.
