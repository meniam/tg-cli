## Goal

Daemon запоминает всё, что загрузил из Telegram (чаты, людей, сообщения целиком), хранит пометки владельца и AI отдельно от данных Telegram и умеет искать по всему этому без обращения к Telegram. Основа для следующих планов: живой поток, глубокая подгрузка истории, папки и состояние аккаунта.

## Scope

- В плане:
  - пакет `internal/store`: одна база на профиль (`<профиль>/store.db`, права 0600), миграции, одна запись и несколько читателей, схема версии 1;
  - пакет `internal/textnorm`: нормализация текста для поиска (регистр, `ё` в `е`);
  - хранение чатов, людей, сообщений (сырой JSON, версии правок, пометка удаления), заготовки таблиц для папок, состояния аккаунта и точек синхронизации (без заполнения из Telegram);
  - пометки к чату, человеку и сообщению: автор владелец или AI, модель, время; добавление, список, удаление;
  - полнотекстовый поиск по чатам, людям, сообщениям и пометкам, с фильтром по автору пометок и со сниппетом;
  - запись в базу «по пути»: то, что Daemon уже получает из Telegram командами `chat list`, `chat resolve`, `chat info`, `message history`, `message get`, `message pinned`, сохраняется; сбой базы не ломает ответ;
  - методы RPC `note.add`, `note.list`, `note.delete`, `search` и команды CLI `note add|list|delete`, `search`;
  - тесты, обновление `AGENTS.md` и `FEATURES.md` (статусы 10.x).
- Вне плана (следующие планы):
  - живой поток и восстановление пропущенных событий, обновление базы из потока;
  - глубокая подгрузка истории по команде, политика скорости;
  - загрузка папок, участников чатов, настроек чатов и состояния аккаунта из Telegram (таблицы создаются пустыми);
  - эмбеддинги, семантический поиск, индекс ссылок;
  - шифрование (защита FileVault и права файла по решению о хранилище).
- Затрагиваются: `internal/{store,textnorm,daemon,rpc,cli}`, `go.mod`, `go.sum`, `AGENTS.md`, `FEATURES.md`.

## Main invariant

- Данные Telegram и пометки лежат в разных таблицах; запись данных Telegram (повторная загрузка, правка, удаление) никогда не меняет и не удаляет пометки.
- Загруженное не теряется: сообщение не удаляется физически, при смене текста сохраняется прежняя версия, удалённое помечается.
- В базу пишет только Daemon, CLI базу не открывает.
- Существующие команды и их ответы не меняются: запись в базу идёт после формирования ответа и её ошибка только логируется (без текста сообщений).
- Код не вызывает ни одного метода Telegram, который меняет данные аккаунта (тест из плана 2 остаётся зелёным).
- `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: поиск молча пропускает слова с `ё` или разным регистром. Стратегия: текст нормализуется при записи в индекс и в запросе одним и тем же кодом (`textnorm`), тесты с кириллицей.
- Риск: массовая запись замедляет ответы. Стратегия: запись в одной транзакции на ответ, один писатель; измерение на тестовых данных; в крайнем случае запись уходит в фоновую очередь (отдельное решение).
- Риск: конкуренция записи и чтения (`SQLITE_BUSY`). Стратегия: WAL, отдельные пулы чтения и записи, `busy_timeout`, как в прототипе.
- Риск: изменение схемы потеряет данные. Стратегия: миграции по `PRAGMA user_version`, тест повторного применения и перехода с версии 0.
- Риск: чужие переписки в одном файле. Стратегия: права 0600, каталог профиля 0700, FileVault (решение о хранилище); текст сообщений не пишется в логи.
- Риск: пометки AI заполняют поиск мусором. Стратегия: автор в каждой записи и фильтр по автору в поиске (решение о пометках).

## Known facts

- Первые два плана закрыты, код закоммичен в ветке плана 2, перед планом 3 ветка создана от её конца.
- Прототип SQLite: вставка 200 000 сообщений без FTS около 3,9 с, с FTS около 13,6 с; база около 700 МБ, из них индекс около 35 МБ; задержка запроса с ранжированием 0,15 до 0,24 с на синтетике.
- Агент Codex `dev` работает в панели Herdr с песочницей: запись только в репозиторий и кэш Go, без сети; новые модули скачивает Claude заранее.

- Шаги 1 и 2 выполнены Codex и проверены Claude (2026-11-13): тесты `-race` зелёные; проверено вручную, что токенизатор `unicode61` режет слова так же, как `textnorm.Query` (эмодзи, `_`, `-` и знаки гласных деванагари разделяют слова), служебные файлы WAL (`-wal`, `-shm`) создаются с правами 0600.
- Замечание к шагу 3: индексируется нормализованный текст; сам токенизатор `unicode61` не складывает `ё` и `е`, поэтому в колонку для индекса всегда идёт `textnorm.Normalize`.

- Шаг 3 принят после доработки (2026-11-13): время первого и последнего появления сделано обязательным во всех таблицах данных Telegram; триггеры обновления индекса срабатывают только при изменении `search_text` (иначе каждое обновление `last_seen_at` перестраивало бы индекс), это закреплено тестом по `sqlite_master`; тесты не зашивают номер версии. Схема лежит в `internal/store/migrations/0002_schema.sql`, версия базы 2 (миграция версии 1 из плана это `0001_init`).
- Замечание к шагу 5: индекс сообщений включает и удалённые (`deleted_at`); поиск по умолчанию должен их отфильтровывать.

- Шаг 4 принят (2026-11-13): `UpsertChats`, `UpsertPeople`, `UpsertMessages`, `MarkMessagesDeleted`, чтение; правило слияния: пустое значение значит «источник не сказал», сохранённое остаётся. Отступление от решения о хранилище: колонка `raw` пока хранит JSON сообщения в том виде, в каком его отдаёт Daemon, а не исходный TL-объект Telegram; настоящий сырой объект появится вместе с синхронизацией.
- Замечание к шагу 6: `out`, `pinned` и другие булевы поля сообщения Daemon передаёт явными значениями (в том числе `false`), иначе слияние сохранит старое значение; поле `pinned` в ответах Daemon пропускается при `false` (`omitempty`), при преобразовании в `store.Message` это надо учитывать.

- Шаг 5 принят (2026-11-13): пометки (`AddNote`, `GetNote`, `ListNotes`, `DeleteNote`, `DeleteNotesByAuthor`) и поиск по четырём областям; сниппет строится из исходного текста, а не из нормализованного индекса; лимит применяется к каждой области отдельно, порядок областей фиксирован (чаты, люди, сообщения, пометки).
- Известное ограничение шага 6b: Daemon знает у человека только отображаемое имя (`rpc.Sender.Name`, `rpc.Chat.Title` для личных чатов), поэтому оно записывается в `people.first_name`; раздельные имя и фамилия появятся с загрузкой полных данных пользователя в плане про синхронизацию.
- Следствие шага 6: `internal/daemon` импортирует `internal/store`, поэтому `internal/cli` зависит от `store` транзитивно через `daemon`. Тест границы проверяет прямой импорт `store` в `cli` и по-прежнему запрещает транзитивные `tgclient` и gotd.

- Шаг 6a принят (2026-11-14): Daemon открывает базу до сокета, методы `note.add|list|delete|delete_by_author` и `search` не требуют входа и соединения, имена `@username` ищутся сначала в базе. Граница `cli` и `store` записана решением [cli зависит от store только через daemon](../decisions/20261114_0005_cli_may_reach_the_store_only_through_the_daemon.md).

- Шаг 6b принят (2026-11-14) с исправлением: Codex передавал число участников 0 как явное значение, и оно стирало настоящее (в `chat.info` ноль означает «не знаем»); теперь `positiveIntPointer`, тест Codex, закреплявший старое поведение, исправлен, добавлен тест `TestChatInfoWithoutMemberCountKeepsTheStoredOne`. Запись идёт синхронно перед возвратом ответа, ошибка базы только логируется без данных из ответа.
