## Goal

Агент может безопасно повторить запись после обрыва или тайм-аута, не создав второго сообщения, и может объявить, под каким аккаунтом команда обязана выполняться, чтобы она не выполнилась под чужим профилем.

## Problem and contract

Тип плана: product (две защиты для записи и чтения).

- Решения владельца (2026-11-14): ожидаемый аккаунт задаётся флагом и переменной окружения; повтор записи безопасен только при ключе идемпотентности, без ключа запись по-прежнему не повторяется.
- Проверка аккаунта (1.7):
  - Глобальный флаг `--expect-user <id или @username>` и переменная `TG_CLI_EXPECT_USER` (флаг сильнее переменной; пусто значит проверки нет). Сверка идёт в Daemon до выполнения обработчика; сравниваются числовой id аккаунта или `username` без учёта регистра.
  - Несовпадение: команда не выполняется (ни чтения, ни записи, ни `--dry-run`), код выхода 4 (`not_authorized`), сообщение называет ожидаемый и фактический аккаунт (id и username, без телефона).
  - Проверка применяется к командам, которые работают с аккаунтом и его базой (`chat`, `message`, `note`, `search`); не применяется к `daemon`, `auth`, `schema`, `version`.
- Идемпотентная запись (2.9, 2.10):
  - Флаг `--idempotency-key КЛЮЧ` у `message send`, `message send-media`, `message poll`, `message forward` (1 до 64 символов `A-Za-z0-9._:-`). У `edit`, `delete`, `react`, `pin`, `unpin` ключа нет: повтор такой записи по природе безопасен (сервер отвечает `MESSAGE_NOT_MODIFIED` или состояние уже достигнуто).
  - Daemon выводит `random_id` Telegram детерминированно из аккаунта, чата, ключа и номера элемента (для альбома, пересылки нескольких сообщений) через SHA-256; повтор с тем же ключом даёт те же `random_id`, и сервер отсекает дубль.
  - Локальная запись `idempotency` в базе (чат, ключ, метод, хэш параметров, результат, время): повтор с тем же ключом и теми же параметрами возвращает сохранённый результат с признаком `replayed: true` без обращения к Telegram; тот же ключ с другими параметрами это код 2 («key was used with different parameters»); запись без результата (обрыв до ответа) значит, что Daemon вызывает Telegram с теми же `random_id` и сохраняет итог.
  - Повтор Daemon'ом (2.10): при ключе Daemon сам повторяет запись один раз после сетевой ошибки или тайм-аута (пауза 1 секунда); без ключа записи не повторяются; FLOOD_WAIT не повторяется (правило дросселя не меняется); чтения Daemon повторяет один раз при переходной сетевой ошибке по явному списку безопасных методов (список составляет шаг 1).
  - Записи хранятся 7 дней, чистятся при старте Daemon и раз в сутки.
  - `--dry-run` показывает, что ключ допустим и есть ли сохранённый результат (`replay_available`).
  - Ответ записи получает необязательное поле `replayed`.
- Релиз одним слоем; откат: откат ветки, таблица `idempotency` остаётся пустой.

## Scope

- В плане: `internal/store` (миграция и таблица `idempotency`), `rpc` (поля параметров и результата, передача ожидаемого аккаунта), `tgclient` (явный `random_id`, повтор при ключе), Daemon (ключ, повтор ответа, проверка аккаунта, `--dry-run`), CLI (`--expect-user`, `TG_CLI_EXPECT_USER`, `--idempotency-key`), схема, тесты, документы, живая проверка в «Браин Тест».
- Вне плана: ключ для `edit`, `delete`, `react`, `pin`, `unpin`; общая очередь отложенных записей; повтор по расписанию; несколько ожидаемых аккаунтов; ключ для `forward` из нескольких источников разными вызовами.
- Затрагиваются: `internal/{store,rpc,tgclient,daemon,cli,schema,exitcode}`, `FEATURES.md`, `docs/cli/`, `docs/contracts.md`, `docs/skill/`, `.agents/decisions/`.

## Main invariant

1. Без `--idempotency-key` запись не повторяется ни Daemon, ни дросселем, и `random_id` остаётся случайным, как сейчас.
2. Одинаковый ключ и одинаковые параметры никогда не создают второго сообщения: либо сохранённый ответ, либо тот же `random_id`.
3. Несовпадение ожидаемого аккаунта останавливает команду до любого обращения к Telegram и до любой записи.
4. Ключ не раскрывает содержимое сообщения; в журнале Daemon ключи и тексты не пишутся.
5. Существующие команды и их ответы без новых флагов не меняются.
6. `internal/cli` не импортирует `tgclient`, gotd, `store`.
7. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: окно отсечения дубля по `random_id` у Telegram короткое. Стратегия: локальная запись результата отвечает на повтор без сервера, сервер нужен только когда ответ потерян; окно измерить на живом аккаунте в границах возможного и записать.
- Риск: ключ использован повторно по ошибке с другим текстом. Стратегия: хэш параметров и код 2.
- Риск: удалённое сообщение возвращается из сохранённого ответа. Стратегия: документировать; ответ несёт `replayed: true`.
- Риск: расхождение `username` аккаунта (может меняться). Стратегия: рекомендовать числовой id, сверять без учёта регистра, при несовпадении называть оба значения.
- Риск: проверка аккаунта замедляет каждую команду. Стратегия: `Self` Daemon держит в памяти, лишнего запроса к Telegram нет.
