## Goal

Агент выгружает всю сохранённую историю чата из локальной базы одним вызовом команды: сообщения от старых к новым, по одному JSON на строку, без Telegram и без входа в аккаунт, с отметкой удалённых.

## Problem and contract

Тип плана: product (новая команда чтения только из базы).

- Решения владельца (2026-11-14): команда `tg message export <чат> --local` (вариант «message export --local»); строка содержит сообщение и признак удаления, версии правок не входят.
- `tg message export <чат> --local [--since T] [--until T] [--include-deleted] [--limit N]`:
  - Источник только локальная база. `--local` обязателен: без него код 2 с пояснением, что выгрузка из Telegram не сделана (14.1, Could). Telegram не вызывается, вход не нужен, Daemon должен работать (как `search` и `message context --local`).
  - Чат задаётся ссылкой, как везде; имя `@username` разрешается по базе, неизвестное в базе даёт `not_found`.
  - Порядок: по возрастанию `id`. Формат только `jsonl`: одна строка, одно сообщение, тех же полей, что отдаёт `message context --local` (`rpc.Message`, собранный из базы функцией `rpcStoredMessage`; полный JSON Telegram не обещается), и поле `deleted` (`true` только у удалённых, у остальных поля нет). Формат по умолчанию `jsonl`; `--format json` и `toon` отклоняются кодом 2, как `jsonl` у не-списков.
  - По умолчанию удалённые сообщения скрыты; `--include-deleted` включает их с `deleted: true`.
  - `--since` и `--until` как у `message history`; `--limit` ограничивает число выгруженных строк (0 или не задан: без ограничения).
  - Пустой результат это успех: ноль строк, код 0, подсказка на stderr (скрывается `--quiet`) с числом выгруженных и подсказкой про `tg chat sync start`.
- Постраничность: один ответ Daemon не больше `MaxFrameSize`, поэтому Daemon отдаёт страницы методом `message.export_local` (курсор это последний `id`, страница до 500 сообщений и не больше размера кадра), а CLI сам листает и печатает строки по мере получения, не накапливая всё в памяти.
- Доступ: закрытый чат не выгружается (`not_found`, тот же ответ, что у неизвестного); политика проверяется на каждой странице.
- Поля чужого текста помечаются `untrusted` в схеме, как у истории (общий тип `rpc.Message`).
- Релиз одним слоем; откат: откат ветки.

## Main invariant

1. Команда не вызывает Telegram ни при каком исходе и не пишет в базу.
2. Закрытый чат невидим (`not_found`), в том числе когда его закрыли между страницами.
3. Каждая страница ответа Daemon помещается в `MaxFrameSize`; выгрузка чата любого размера не упирается в лимит кадра.
4. Каждое сохранённое неудалённое сообщение чата выгружается ровно один раз, без пропусков и повторов на границах страниц.
5. Существующие ответы `json` и `jsonl` других команд не меняются.
6. `internal/cli` не импортирует `tgclient`, gotd, `store`.
7. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: сырой JSON сообщения с большим вложением раздувает страницу выше кадра. Стратегия: страница режется по размеру кадра, как у `message history` (`MaxBytes`), курсор указывает на остаток; одно сообщение больше кадра отдаётся единственным в странице или даёт понятную ошибку (решает шаг 1).
- Риск: удалённое сообщение вернулось (повторная запись сбрасывает `deleted_at`). Стратегия: выгрузка отражает базу как есть, поведение записи не меняется.
- Риск: агент принимает выгрузку за полную историю чата. Стратегия: подсказка в stderr и в навыке: выгружено только сохранённое, полнота через `chat sync` (`sync_state.complete`).
- Риск: поток JSONL разрывается посреди выгрузки при остановке Daemon. Стратегия: код выхода не 0, уже напечатанные строки остаются корректными, продолжение по последнему `id` (подсказка с `--since` не годится, поэтому курсор в stderr при ошибке).

## Known facts

- Аудит шага 1 (Codex, 2026-11-14, отчёт `var/agents/plans/20261114_1749_local_message_export/audit.md`, в git не входит):
  - `message.context --local` разрешает имя только по базе и применяет политику без входа в аккаунт (`internal/daemon/discovery.go:138-173`); `message.history` требует вход и для имени может вызвать Telegram (`internal/daemon/access.go:29-64`), поэтому берём путь `context --local`.
  - Запрос `WHERE chat_id=? AND id>? ORDER BY id LIMIT ?` идёт по `sqlite_autoindex_messages_1` без сортировки (15 000 строк, SQLite 3.54.0); с условиями по `date` SQLite выбирает `messages_chat_date_idx` и сортирует отдельно. Новый индекс не нужен; замера Go-драйвера на большом чате нет.
  - `messages.raw` хранит `rpc.Message`; `rpcStoredMessage` (`internal/daemon/discovery.go:175-209`) собирает его из строки, но не переносит `Sender.Username` из `raw`; `deleted_at` в `rpc.Message` нет, `deleted` добавляем сами.
  - Тест пути потока в `messages` есть только для `message.new` (`TestEventAccessAndDeduplication`); для `message.edit` и `deleted_at` после `message.delete` нет.
  - Сообщение больше `MaxFrameSize` в `message.history` рвёт транспорт (код 1 в CLI); писатель кадра размер не проверяет.
  - `just check` в песочнице Codex падает на сокетах (ограничение среды); на стороне Claude зелёный.

- Поток уже пишет новые сообщения, правки и удаления в `messages` (`internal/daemon/events.go`).
- Лимит кадра RPC 1 МиБ (`rpc.MaxFrameSize`), поэтому выгрузка постраничная.
