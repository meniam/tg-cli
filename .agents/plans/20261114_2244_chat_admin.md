## Goal

Агент вступает в чат и выходит из него, создаёт супергруппу или канал, меняет название и описание, исключает, банит и разбанивает участника, ограничивает права участника и права по умолчанию, включает slow mode. Каждое действие проходит барьер владельца (списки в `access.json`), имеет `--dry-run`, не повторяется и даёт предсказуемый код выхода на ошибку прав.

## Problem and contract

Тип плана: product (новая группа команд записи, которые меняют чужие права и состав чата).

Эти команды опаснее записи сообщений: сообщение можно удалить, а исключённый человек может не вернуться в закрытый чат, бан виден всем, выход из закрытого чата лишает доступа к истории. Поэтому контракт строится от барьера, а команды вторичны. Ниже предложение планировщика; пункты со ссылкой на `Qn` зависят от ответа владельца и могут поменяться.

### Команды (предложение, имена по образцу установленного `tg`)

| Команда | RPC | Telegram (супергруппа или канал / обычная группа) | Ответ |
| --- | --- | --- | --- |
| `tg chat join <чат\|ссылка-приглашение> [--dry-run]` | `chat.join` | `channels.joinChannel` / по ссылке `messages.importChatInvite` | `{chat_id, type, already_member, requested}` |
| `tg chat leave <чат> --yes [--dry-run]` | `chat.leave` | `channels.leaveChannel` / `messages.deleteChatUser` с собой | `{chat_id, left}` |
| `tg chat create <название> --type supergroup\|channel [--about ТЕКСТ] [--dry-run]` | `chat.create` | `channels.createChannel` (`megagroup` или `broadcast`) | `{id, type, title}` (Q4) |
| `tg chat edit <чат> [--title ТЕКСТ] [--about ТЕКСТ] [--dry-run]` | `chat.edit` | `channels.editTitle` / `messages.editChatTitle`; описание `messages.editChatAbout` | `{chat_id, title_changed, about_changed}` |
| `tg chat kick <чат> <пользователь> --yes [--dry-run]` | `chat.kick` | `channels.editBanned` (Q6) / `messages.deleteChatUser` | `{chat_id, user_id, kicked}` |
| `tg chat ban <чат> <пользователь> [--until ВРЕМЯ] --yes [--dry-run]` | `chat.ban` | `channels.editBanned` с `view_messages` | `{chat_id, user_id, banned, until}` |
| `tg chat unban <чат> <пользователь> [--dry-run]` | `chat.unban` | `channels.editBanned` с пустыми правами | `{chat_id, user_id, banned: false}` |
| `tg chat restrict <чат> <пользователь> (--deny a,b,... \| --clear) [--until ВРЕМЯ] [--dry-run]` | `chat.restrict` | `channels.editBanned` без `view_messages` | `{chat_id, user_id, denied, until}` |
| `tg chat permissions <чат> (--deny a,b,... \| --clear) [--dry-run]` | `chat.permissions` | `messages.editChatDefaultBannedRights` (оба типа) | `{chat_id, denied}` |
| `tg chat slow-mode <чат> <секунды> [--dry-run]` | `chat.slow_mode` | `channels.toggleSlowMode` (только супергруппа) | `{chat_id, seconds}` |

- `<пользователь>` это `@username` или положительный id (как у `chat common`); чат, канал или отрицательный id дают код 2; сам аккаунт как цель `kick|ban|restrict` даёт код 2 с подсказкой `use chat leave`.
- `--until` принимает RFC 3339, как `--since` и `--until` чтения; Daemon требует от 30 секунд до 366 дней от текущего времени, иначе код 2 (Telegram считает значение вне этих границ вечным, а мы не даём получить вечный бан по ошибке). Без `--until` бан и ограничение бессрочны.
- `--deny` задаёт полный набор запретов, а не добавку: так устроен `ChatBannedRights` (каждый вызов заменяет набор). `--clear` снимает все запреты. Имена прав (предложение, точное соответствие полям фиксирует шаг 1): `send-plain`, `send-media`, `send-photos`, `send-videos`, `send-roundvideos`, `send-audios`, `send-voices`, `send-docs`, `send-stickers`, `send-gifs`, `send-games`, `send-inline`, `send-polls`, `embed-links`, `send-reactions`, `change-info`, `invite-users`, `pin-messages`, `manage-topics`. `view-messages` в `--deny` недоступно: это бан, для него `chat ban`.
- `chat edit`: нужен хотя бы один из `--title` и `--about`; `--about ""` очищает описание; название от 1 до 128 символов, описание до 255 (договорные пределы, шаг 1 сверяет). Флаг называется `--about`, как поле `ChatInfo.about` (у установленного `tg` он `--description`).
- `chat slow-mode`: секунды из набора `0, 10, 30, 60, 300, 900, 3600` (допущение по клиентам Telegram, шаг 1 сверяет с `SECONDS_INVALID`); `0` выключает. Обычная группа даёт код 2 `slow mode needs a supergroup` (миграция группы вне плана).
- Обычная группа: `ban`, `unban`, `restrict` дают код 2 (у обычной группы нет персональных прав, только `kick` и права по умолчанию). Канал: `restrict`, `permissions` и `slow-mode` дают код 2 (в канале не пишут участники).
- Личный чат, бот и «Избранное» для любой команды кроме `join` дают код 2.

### Барьер записи (главное)

Порядок проверок одинаков для всех команд группы и повторяет `writeReference`:

1. CLI: разбор аргументов и флагов, код 2 без вызова Daemon. Для команд с `dangerous: true` (Q5) нет `--yes` и нет `--dry-run`: код 2, Daemon не вызывается.
2. Daemon: аккаунт вошёл (иначе код 4); проверка ожидаемого аккаунта, если поток идемпотентности уже слит (`expect_user`, код 4).
3. Видимость чата: закрытый списками `allow`/`block` чат отвечает тем же `not_found`, что неизвестный (числовой id: `ErrUnknownChatID`, остальные ссылки: `ErrChatNotFound`), до любого вызова записи.
4. Разрешение владельца: для админ-команд чат в списке, который выбирает Q1; для `join` и `leave` по Q2; для `create` по Q4. Нет разрешения: код 9 `write_disabled` (RPC `-32008`) с подсказкой, какой список дополнить (Q1b). Закрытая политика (`access.json` не разобран или с правами записи для группы) выключает всё, как сегодня.
5. Цель-пользователь: разбор, разрешение через Telegram (чтение), правило видимости по Q12, запрет на себя.
6. Совместимость типа чата с командой и значения (`--until`, `--deny`, секунды, длины): код 2.
7. `--dry-run` останавливается здесь и возвращает `dry_run: true`, `action`, `chat_id`, `user_id` (если есть), `count: 1` и проверенные параметры без текстов названия и описания (только длины). По Q10 dry-run дополнительно читает свои права администратора.
8. Журнал модерации (Q9): строка `phase: "intent"` до вызова; сбой её записи отменяет действие.
9. Один вызов Telegram, без повторов: все новые запросы добавляются в `writeRequest` дросселя, FLOOD_WAIT возвращается кодом 6 с секундами и не повторяется ни Daemon, ни дросселем.
10. Строка `phase: "result"` журнала; best-effort сохранение чата в базу (`saveChats`) для `join`, `create`, `edit`, если чат виден по спискам. Закрытый чат в базу не пишется (9.2.6).

Политика перечитывается на каждый запрос (`d.policy()`), как у остальной записи; кэш Daemon не держит разрешений между запросами.

## Main invariant

1. Без разрешения владельца на чат (список по Q1, Q2, Q4) и без видимости чата ни один запрос записи из этого плана в Telegram не уходит; закрытый чат отвечает как неизвестный; тест считает вызовы подмены и ждёт ноль.
2. `--dry-run` не вызывает методы записи Telegram и не пишет журнал модерации и базу.
3. Команды с `dangerous: true` без `--yes` и без `--dry-run` не доходят до Daemon (код 2).
4. Повторов записи нет; FLOOD_WAIT не повторяется (все новые запросы в `writeRequest`, тест на один вызов).
5. Существующие команды, их ответы, коды выхода и разбор `access.json` без новых полей не меняются; файл без новых полей даёт ту же политику, что сегодня.
6. `internal/cli` не импортирует `tgclient`, gotd, `store`; `readFiles` в `readonly_test.go` не пополняются файлами записи.
7. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: агент банит или исключает не того человека (одинаковые имена, устаревший `username`). Стратегия: цель по числовому id предпочтительна (навык и `docs` это говорят), `--dry-run` возвращает `user_id`, `--yes` у необратимых команд (Q5), журнал модерации (Q9).
- Риск: исключение из закрытого чата необратимо для человека (без ссылки он не вернётся). Стратегия: `kick` и `ban` опасные, `unban` есть; предупреждение в навыке.
- Риск: выход из закрытого чата лишает аккаунт доступа к истории. Стратегия: `leave` опасная, `--dry-run`, в навыке совет сначала `chat sync`.
- Риск: разрешение `write` молча расширится до модерации в чатах, которые владелец открыл только для сообщений. Стратегия: отдельный список `admin` (Q1, рекомендация).
- Риск: массовое создание каналов ведёт к `CHANNELS_TOO_MUCH` и к ограничению аккаунта (`USER_RESTRICTED`). Стратегия: отдельное разрешение на создание (Q4), без повторов, ошибки лимита кодом 5.
- Риск: `kick` в супергруппе это два вызова (бан и снятие бана, Q6): при сбое второго человек остаётся забанен. Стратегия: ответ сообщает `still_banned: true` и код 5, журнал пишет обе фазы, `unban` исправляет.
- Риск: новые методы не попадут в `writeRequest` и повторятся на FLOOD_WAIT. Стратегия: тест «каждый запрос `chat_admin.go` есть в `writeRequest`» по списку из этого плана.
- Риск: поле `access.json`, которое добавит владелец, закроет всё после отката на старую сборку (неизвестное поле, 9.2.5). Стратегия: предупреждение в Deploy / rollback и в `docs/cli/access.md`.
- Риск: конфликт слияния с соседними потоками в общих файлах. Стратегия: вставки только из таблицы выше, отдельными строками; порядок слияния в разделе «Пересечения».
- Риск: живая проверка задевает реальных людей. Стратегия: только тестовый чат и цель, которые назовёт владелец (Q13); без ответа живая проверка ограничивается `--dry-run` и ошибками барьера.

### Q1. Какое разрешение открывает админ-команды (`edit`, `kick`, `ban`, `unban`, `restrict`, `permissions`, `slow-mode`)

- A (рекомендую): новый список `admin` в `access.json` (id чатов, как `write`); чат должен быть в `admin`, видим и не в `block`; `write` не нужен и не достаточен. Цена: поле в `access`, счётчик в `daemon status`, раздел в документах, примерно полдня шага 2; владелец заводит второй список.
- B: тот же список `write`. Цена: ноль кода; но каждый чат, где агенту уже разрешены сообщения, сразу открыт для банов и смены прав без нового решения владельца.
- C: нужны оба списка, `write` и `admin`. Цена: как A плюс двойная настройка; защищает от опечатки в одном списке.
- Статус: принято (вариант A), блокирует шаг 2.

### Q1b. Какой код выхода у отказа по списку `admin`

- A (рекомендую): прежний код 9 `write_disabled` (RPC `-32008`), сообщение и `data.list: "admin"` называют список. Цена: ноль новых кодов, `exitcode` не трогается (его правит поток идемпотентности).
- B: новый код 10 `admin_disabled`. Цена: правка `internal/exitcode`, таблиц в README, `AGENTS.md` и `tg schema`, конфликт с потоком идемпотентности.
- Статус: принято (вариант A), блокирует шаг 2.

### Q2. Что разрешает `join` и `leave`

- A (рекомендую): чат в `write`; для `join` по `@username` id сначала разрешается чтением и проверяется. Цена: чтобы агент вступил в группу, владелец открывает её и для сообщений.
- B: чат в `admin`. Цена: смешивает участие с модерацией; в чужие публичные группы агент без прав админа вступать не будет вовсе, если владелец не хочет давать модерацию.
- C: любой видимый чат, `join` без подтверждения, `leave` с `--yes`. Цена: ноль настройки; вступление видно участникам и тратит лимит 500 каналов без решения владельца.
- Статус: принято (вариант A), блокирует шаг 2.

### Q3. Вступление по ссылке в закрытый чат, id которого до вступления не виден

- A (рекомендую): отказ кодом 9 с подсказкой «владелец вступает сам»; по ссылке можно вступить, только если `checkChatInvite` вернул чат (`already_member` или предпросмотр) и его id разрешён по Q2. Цена: агент не вступает в новые закрытые чаты по одной ссылке.
- B: вступать при пустом `allow` и `--yes`; если после вступления чат в `block`, сразу выйти и ответить `not_found`. Цена: вступление и выход видны участникам; лишние два вызова.
- C: новое поле `access.json` со списком разрешённых ссылок. Цена: ещё одно поле, хранение хэшей приглашений в файле владельца.
- Статус: принято (вариант A), не блокирует шаги 2–3 для `join` по id и `@username`.

### Q4. Создание чата: разрешение и типы

- A (рекомендую): только `--type supergroup|channel`, без приглашённых, при булевом поле `"create": true` в `access.json`; новый чат не попадает ни в один список, ответ даёт `id`, владелец сам добавляет его в `write` или `admin`. При непустом `allow` новый чат закрыт: ответ только `{id, type, closed: true}`, в базу не пишется. Цена: поле в `access`, одна строка в статусе.
- B: как A, но без поля, с `--yes`. Цена: ноль настройки; агент может создавать каналы без решения владельца (лимит и риск `USER_RESTRICTED`).
- C: плюс обычная группа с `--user` (нужен хотя бы один приглашённый, `USERS_TOO_FEW`). Цена: приглашение людей без их согласия, вопрос приватности, больше кода и тестов.

- B: `--yes` у всех команд, которые меняют чужие права (плюс `restrict`, `permissions`, `slow-mode`, `edit`, `unban`). Цена: больше трения; `--yes` теряет вес как сигнал необратимости.

- Статус: принято (вариант A), блокирует шаг 5.
