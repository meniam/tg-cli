## Goal

Агент скачивает медиа сообщений в каталог, который разрешил владелец, без выхода за него, без перезаписи и с пределом размера. Агент выгружает всех участников чата в JSONL одной командой. Агент пересылает сообщения копией без автора и получает ясный отказ, когда чат защищён от копирования. Скачивание и копирование защищённого контента не делаются (рекомендация Q5, Q8).

### Контракт для рекомендованных вариантов Q1 до Q9

Другой ответ меняет отмеченные места.

**Скачивание (6.3).**

- Команда (Q4): `tg message download <чат> <id>... --output <каталог> [--dry-run]` или `tg message download <ссылка t.me на сообщение> --output <каталог>`, ссылки разбирает `chatref`, как у `message get`. От 1 до 20 id за вызов (Q2). Класс безопасности `local_write`, без `--yes`.
- Где можно писать (Q1): новое поле `downloads` в `access.json`, массив абсолютных путей каталогов без повторов, отдельно от `files`. Без поля или с пустым массивом команда отвечает кодом 9 до обращения к Telegram и подсказывает владельцу поле `downloads`. Агент `access.json` не правит.
- `--output` обязателен, абсолютный, указывает на существующий каталог внутри одного из корней `downloads` после разрешения символических ссылок. Каталоги Daemon не создаёт. Путь вне корней, относительный путь, файл вместо каталога дают код 2 до обращения к Telegram.
- Запись идёт через `os.Root`, открытый на корне `downloads`: имя файла внутри корня не выходит наружу ни через `..`, ни через символическую ссылку, подменённую во время скачивания. Файл сначала пишется во временный `.<имя>.part` с `O_CREATE|O_EXCL` и правами 0600, затем ставится под итоговое имя без перезаписи (жёсткая ссылка внутри `os.Root`, затем удаление временного; если итоговое имя занято, ошибка элемента). При ошибке, отмене и превышении предела временный файл удаляется.
- Имя файла (Q3): `<chat_id>_<message_id>.<ext>`, расширение из короткого списка по MIME (`jpg`, `png`, `webp`, `gif`, `mp4`, `mov`, `webm`, `ogg`, `oga`, `mp3`, `m4a`, `pdf`, `zip`, `txt`), иначе `bin`; фото всегда `jpg`. Исходное имя документа из Telegram в путь не попадает, оно возвращается полем `file_name` с пометкой `untrusted`.
- Пределы (Q2): 100 MiB на файл и 500 MiB на вызов. Размер известен до скачивания (`Document.Size`, размер наибольшего `PhotoSize`): файл больше предела не скачивается, ошибка элемента. Запись дополнительно считает байты и обрывается на пределе, если Telegram отдал больше заявленного.
- Что скачивается: фото (наибольший размер, без `stripped`) и документ (видео, аудио, голосовое, кружок, стикер, GIF, файл). Сообщение без медиа, с медиа другого вида (опрос, геоточка, контакт, веб-страница, платное медиа, история) даёт ошибку элемента `no downloadable media`. Альбом не раскрывается: каждый id это одно сообщение.
- Защищённый контент (Q5): если у сообщения `noforwards` или у чата `noforwards`, файл не скачивается, ошибка элемента код 5 (`telegram`) с текстом `content is protected: saving media is not allowed`. Проверка до первого запроса `upload.getFile`.
- Путь запроса: Daemon проверяет `--output` и `downloads`, разбирает ссылку на чат, проверяет видимость (закрытый чат `not_found`), одним запросом получает сообщения по id (`messages.getMessages` или `channels.getMessages`) со свежим `file_reference`, затем качает по одному файлу через `telegram/downloader` в один поток (многопоточность это 6.4, вне плана). Запросы `upload.getFile` и `upload.getCdnFile` идут через дроссель в нижней очереди, как части отправки.
- Ответ `DownloadResult`: `chat_id`, `files` (элементы `message_id`, `path` абсолютный, `size`, `media_type`, `mime`, `file_name` untrusted), `dry_run`, плюс общий блок частичного успеха `Batch` (`partial`, `errors` с `id` и кодом), как у пересылки. Все id упали: команда завершается кодом первой ошибки. `--dry-run` получает сообщения, считает имена, размеры и проверки и не пишет на диск. `--format jsonl` печатает по файлу в строке (`ItemPath: files`).
- Метод JSON-RPC `message.download`, тайм-аут 600 секунд, как у `message.send_media`. Скачанное не записывается в базу; миграция не нужна.
- Журнал Daemon пишет метод, длительность и код, без путей и имён файлов.

**Защищённые чаты (6.5).** Рекомендация Q5: не делать, пункт 6.5 получает тег `[Wont]` с причиной «правила Telegram запрещают клиенту сохранять медиа защищённых сообщений; вход идёт по ключам официального клиента, нарушение ставит под удар аккаунт». Код отказа описан выше.

**Выгрузка (14.1).**

- Сообщения (Q6): отдельной выгрузки из Telegram нет. Путь: `tg chat sync start <чат>`, дождаться `tg chat sync status`, затем `tg message export <чат> --local`. План меняет только текст помощи `message export` (вместо «not implemented» рецепт из двух шагов), справочник, навык и статус 14.1.
- Участники и подписчики (Q7): флаг `--all` у `tg chat members`. CLI сам обходит страницы по 200 через существующий метод `chat.members` до исчезновения `next_offset` и печатает JSONL по участнику (`--format jsonl` обязателен с `--all`, как у `message export`; другие форматы код 2). `--all` несовместим с `--offset` и `--limit` (код 2), совместим с `--filter` и `--search`. Daemon и Telegram-слой не меняются; дроссель держит темп; при ошибке после напечатанных строк в stderr пишется `last offset N`. Подписчики канала доступны только администратору: Telegram отвечает `CHAT_ADMIN_REQUIRED`, это существующий код. Предел сервера для больших групп (около 10000 участников) описывается в справочнике, шаг 1 уточняет.

**Пересылка (14.3).**

- Фоллбэк (Q8): автоматического обхода защиты нет. Новые флаги `message forward --copy` (поле `DropAuthor`: копия без заголовка «Переслано от») и `--no-captions` (поле `DropMediaCaptions`, только вместе с `--copy`, иначе код 2). Без новых флагов запрос в Telegram не меняется. Ошибка `CHAT_FORWARDS_RESTRICTED` переводится в код 5 с текстом `forwarding from this chat is restricted (protected content)` для каждого элемента пачки.
- Маршрутизация (Q9): движок правил не делается, агент сам выбирает получателя и вызывает `message forward` для каждого. В `FEATURES.md` 14.3 делится: копия и ясный отказ делаются, маршрутизация `[Wont]`.
- `--copy` и `--no-captions` входят в ключ идемпотентности автоматически (каноническая форма параметров), запись разрешена только в чат из `write`, как сейчас.

**Релиз и откат.** Один слой; откат ветки. Схема базы не меняется. `access.json` с полем `downloads` после отката ветки не разбирается старым кодом (неизвестный ключ закрывает все чаты): перед откатом владелец убирает поле. Это записывается в справочник и в «Deploy / rollback».

## Main invariant

1. Daemon пишет файлы только внутри корня `downloads`: ни `..`, ни символическая ссылка, ни подмена каталога во время записи не выводят запись наружу; существующий файл не перезаписывается; права файла 0600; после ошибки и отмены временного файла нет.
2. Без `downloads` в `access.json` ни один запрос к Telegram по `message download` не уходит (код 9).
3. Медиа защищённого сообщения или чата не скачивается: `upload.getFile` для него не вызывается.
4. Файл больше предела не скачивается, сумма за вызов не превышает предела.
5. Закрытый списками доступа чат отвечает как неизвестный.
6. `message forward` без новых флагов шлёт тот же запрос, что сейчас; остальные команды и ответы не меняются, кроме текста помощи `message export`.
7. Схема базы не меняется; `internal/cli` не импортирует `tgclient`, gotd, `store`.
8. Ни тест, ни проверка по умолчанию не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: обход корня через символическую ссылку или гонку «проверил, потом открыл». Стратегия: только `os.Root`, открытый один раз на корень; путь `--output` переводится в относительный от корня после `EvalSymlinks`; тесты с ссылкой внутрь и наружу, с подменой каталога на ссылку между проверкой и записью, с `..` в имени.
- Риск: имя из Telegram ведёт в чужой путь или ломает терминал. Стратегия: имя генерирует Daemon, исходное только в поле `file_name` с пометкой `untrusted`.
- Риск: заполнение диска. Стратегия: пределы Q2 до скачивания и счётчик байт при записи; число файлов за вызов ограничено.
- Риск: правка `internal/access/access.go` пересекается с другими потоками третьей волны (`channels_profile`, `dialogs_manage`, `message_extras` стартовали от того же `b8330a8`), если они тоже добавят ключи. Стратегия: вставки отдельными строками; при конфликте сохраняются обе стороны; тест разбора всех ключей вместе.
- Риск: откат ветки с полем `downloads` в `access.json` закроет все чаты (неизвестный ключ). Стратегия: строка в «Deploy / rollback» и в справочнике `access.md`.
- Риск: `downloader` сам повторяет запросы или не обрабатывает `FILE_REFERENCE_EXPIRED`, CDN, FLOOD_WAIT так, как ждёт дроссель. Стратегия: шаг 1 читает исходники `telegram/downloader`; при необходимости обёртка с одной повторной выборкой сообщения на `FILE_REFERENCE_EXPIRED`; FLOOD_WAIT дольше порога даёт код 6, файл удаляется.
- Риск: долгая загрузка держит слот RPC и упирается в тайм-аут 600 с. Стратегия: пределы Q2; шаг 8 меряет скорость на файле 50 до 100 MiB; при нехватке времени отдельный вопрос, а не молчаливое увеличение.
- Риск: `--copy` в защищённом чате ждут как обход. Стратегия: Telegram сам отказывает (`noforwards` чата запрещает и копию), код 5 с понятным текстом; навык это объясняет.
- Риск: `chat members --all` на большой группе долго идёт и ловит FLOOD_WAIT. Стратегия: страницы через дроссель, `last offset` в stderr для продолжения через `--offset`; живая проверка только на небольшой группе.

## Known facts

- `access.json` разбирается строго: неизвестный ключ даёт ошибку, а ошибка закрывает все чаты (`parse`, `default: unknown field`; `Loader.Policy` возвращает `denyAll`).
- `files` хранит абсолютные очищенные пути без повторов (`parseFileRoots`); проверка корня при чтении идёт через `EvalSymlinks` до и после открытия и `os.SameFile` (`fileroot.Open`). Для записи такого кода нет.
- Отправка медиа ограничена 100 MiB на файл и на альбом (`fileroot.MaxFileSize`), тайм-аут `message.send_media` 600 с (`daemon.go:330`).
- В базе у сообщения есть только `media_type` (`0002_schema.sql`, `rpc.Message.MediaType`); места файла и `file_reference` не хранятся, поэтому перед скачиванием сообщение запрашивается заново.
- Дроссель отправляет части загрузки (`upload.saveFilePart`, `upload.saveBigFilePart`) в нижнюю очередь и не повторяет их на FLOOD_WAIT; `upload.getFile` сейчас классифицируется как обычный запрос (`classifyRequest`, ветка `default`).
- `forwardBatches` строит `MessagesForwardMessagesRequest` с `FromPeer`, `ToPeer`, `ID`, `Silent`, `RandomID`; `DropAuthor` и `DropMediaCaptions` не заполняются.
- `chat members` отдаёт до 200 за страницу (`listLimit(p.Limit, 200)`), `next_offset` по `Count` для супергрупп и по полному списку для обычных групп; участники сохраняются в базу (`saveMembers`).
- `message export` без `--local` отвечает кодом 2 с текстом «export from Telegram is not implemented» (`export_cmd.go:52`).
- Коды RPC: `CodeTelegram` −32002 (выход 5), `CodeNotFound` −32006 (7), `CodeWriteDisabled` −32008 (9), `CodeInvalidParams` (2).
- Другие потоки третьей волны: worktree `tg-cli-channels_profile`, `tg-cli-dialogs_manage`, `tg-cli-message_extras` от того же `b8330a8`; их планов на момент записи нет, пересечения в общих файлах не проверены.
