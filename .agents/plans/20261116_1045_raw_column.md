### Контракт

**Сериализатор (новый пакет `internal/tgraw`).** `tgraw.Marshal(obj) (json.RawMessage, error)` принимает объект gotd (`tdp.Object`), обходит поля по `TypeInfo().Fields` и отражению:

- первый ключ `"_"`: имя конструктора TL из `TypeName()` (`"message"`, `"channel"`, `"peerUser"`); дальше поля в порядке схемы под именами схемы (`SchemaName`: `from_id`, `edit_date`);
- пропускаются: поля с `Null` (флаг не выставлен), нулевые значения Go (`0`, `false`, `""`, `nil`, пустой срез), служебное поле `flags`;
- вырезаются: `access_hash` на любой глубине; `hash` внутри объекта `authorization` (ключ сессии, контракт «raw session hash remains private», `docs/contracts.md:52`);
- `[]byte` идёт строкой base64 (`file_reference`, `stripped_thumb`); `int64` идёт числом; вложенные интерфейсы (`PeerClass`, `MessageMediaClass`) раскрываются в объект со своим `"_"`; срезы в массивы;
- вывод детерминирован (одинаковый объект даёт одинаковые байты) и всегда проходит `json_valid`;
- неизвестный вид поля даёт ошибку, а не молчаливый пропуск.

`internal/tgraw` импортирует только gotd и стандартную библиотеку; его импортирует только `internal/tgclient`. `rpc`, `store`, `daemon`, `cli` по-прежнему не зависят от gotd.

**Что кладётся в `raw` (правило строки).**

1. Ответ-список (один вызов, много строк: `messages.getHistory`, `messages.getDialogs`, `contacts.getContacts`, `account.getAuthorizations`, `contacts.getBlocked`, `messages.getDialogFilters`): в строку идёт её элемент списка (`message`, `channel`, `user`, `authorization`, `peerBlocked`, `dialogFilter`, `dialog`), а не весь ответ.
2. Ответ на одну строку (`users.getFullUser`, `channels.getFullChannel`, `messages.getFullChat`, `account.getNotifySettings`, `messages.transcribeAudio`): объект ответа целиком, вместе с массивами `chats` и `users`. Закрытые чаты в них не вычищаются (Q1 = C, решение владельца).
3. Обновление (`events`, ответ транскрипции из потока): объект обновления (`updateNewMessage`, `updateEditMessage`, `updateDeleteMessages`, `updateDeleteChannelMessages`, `updateMessageReactions`, `updateTranscribedAudio`).
4. Строка из нескольких ответов (`chats`, `people`, `transcriptions`): объект `{"<метод>": <объект по пунктам 1-3>, ...}`. Ключ это имя метода TL (`"messages.getDialogs"`, `"channels.getFullChannel"`); для обновления имя конструктора (`"updateTranscribedAudio"`). Новый ответ того же метода заменяет только свой ключ, остальные ключи остаются. У остальных таблиц ключей методов нет: `raw` целиком заменяется последним ответом (решение владельца).
5. Ответ записи сообщения (`sendMessage`, `editMessage`, `sendMedia`, опрос, стикер): если в ответе есть объект сообщения (`updateNewMessage`, `updateNewChannelMessage`, `updateEditMessage`, `updateEditChannelMessage`), в `messages.raw` идёт он; если ответ короткий (`updateShortSentMessage` без сообщения), остаётся JSON Daemon, как сейчас, до следующего чтения из Telegram.
6. Ошибка сериализации не роняет команду: Daemon пишет одну строку в журнал (тип объекта и текст ошибки, без данных), `raw` остаётся `NULL` (у `messages` JSON Daemon, колонка `NOT NULL`).

## Scope

- В плане: сериализатор; миграция `0009`; поля `Raw` в `rpc`; заполнение в `tgclient` по карте источников; запись в `store` для 12 таблиц; перенос `people.raw` в `people.deleted` и `folders.raw` в `folders.data`; проверка `json_valid` у `message_versions`; сохранение `raw` в `chat_versions`; измерение роста на копии базы; документы и статусы `FEATURES.md`.
- Вне плана: бинарный TL; команда просмотра `raw`; выдача `raw` в ответах CLI или через JSON-RPC; запись `edited_at`; заполнение `raw` у старых строк без нового чтения из Telegram (отдельной перезагрузки нет); `raw` у отправителей из ответов истории и поиска; `raw` у `account_state`, `owner_snapshots`, `notes`, `note_tags`, `sync_state`, `folder_chats`, `idempotency`, `meta`; сжатие и ограничение размера `raw`; хранение номера слоя TL; живые проверки.

## Main invariant

1. Ответы CLI и JSON-RPC не меняются байт в байт: `tg schema` до и после совпадает (`diff` пуст), ни один ответ не содержит ключа `raw`, `idempotency.result` прежний.
2. Запросы в Telegram не меняются: ни одного нового вызова, `raw` берётся только из уже полученных ответов.
3. Чтения из локальной базы (`message export --local`, `message export-month`, `message context --local`, `folder list`, `contact list`, `chat changes`, VIEW `chats_state`, повтор событий) дают те же ответы на старых строках (`0008`) и на новых.
4. В `raw` нет `access_hash` и нет `hash` объекта `authorization` ни на какой глубине.
5. Агент не получает `raw` ни одной командой, и закрытые чаты, упомянутые в `raw` разрешённых строк (массивы `chats`/`users`, пиры папок, `fwd_from`), не появляются ни в одном ответе CLI и JSON-RPC, ни в файлах `export-month`, ни в поиске (Q1 = C). Строки закрытых чатов, как и раньше, не пишутся.
6. Миграция `0009` на базе `0008` не теряет данных: число строк всех таблиц прежнее, `people.deleted` совпадает со старым `raw.deleted`, `folders.data` со старым `folders.raw`, триггер версий и VIEW работают; невалидный JSON в `message_versions.raw` (у владельца 0 строк) становится `NULL`.
7. `rpc`, `store`, `daemon`, `cli` не импортируют gotd; ни тест, ни проверка не обращаются к живому Telegram; `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: база растёт сильнее ожидаемого (решение владельца: «для сообщений raw примерно удвоит строку»; `stripped_thumb` и размеры фото в base64; массивы `chats`/`users` в ответах на одну строку). Стратегия: измерение на копии в шаге 10 до слияния; при росте файла больше чем вдвое план `blocked` и вопрос владельцу.
- Риск: отражение медленное на странице истории (100 сообщений, пауза между страницами 2 секунды). Стратегия: бенчмарк в шаге 2; ориентир меньше 5 мс на страницу из 100 сообщений; если хуже, кэш описаний полей по типу.
- Риск: тип gotd с полем, которое сериализатор не знает (`bin.Int128`, `bin.Int256`, `tg.JSONValueClass`, вложенный `bin.Fields`). Стратегия: ошибка вместо пропуска, правило 6 контракта, тест по реестру `tg.TypesConstructorMap()`: все конструкторы с нулевыми полями сериализуются без ошибки.
- Риск: `raw` разрешённой строки хранит название и id закрытого чата (Q1 = C), и новый код начнёт читать `raw` в ответ агенту. Стратегия: разбор JSON Daemon только без `"_"`, перенос `deleted` и папок в свои колонки (шаги 3, 5), тест шага 9 по всем командам, читающим базу, и тест-сторож на чтение `Raw` в Daemon; правило в справочнике (шаг 11).
- Риск: перестройка `message_versions` ломается на версии SQLite драйвера или оставляет таблицу без `STRICT`. Стратегия: тест обновления с `0008` с данными и `PRAGMA integrity_check`; `TestSchemaMigration` со списком STRICT-таблиц.
- Риск: слияние по ключам методов в `chats` перетирает чужие ключи при гонке двух записей. Стратегия: `UpsertChats` уже читает и пишет строку в одной транзакции записи; `SaveChatFull` и `UpdateTranscription` сливают ключ в SQL через `json_set` одним `UPDATE`.
- Риск: `json_patch` сливает вложенные объекты рекурсивно и оставил бы устаревшие поля. Стратегия: только `json_set` по ключу метода, `json_patch` не используется.
- Риск: формат `raw` меняется при обновлении gotd (новые поля, переименования схемы). Стратегия: записать в решение; хранение слоя вне плана.
- Риск: `raw` хранит то, чего не было в базе: IP, страну и регион сессий, звуки уведомлений, телефон в объекте `user` (телефон уже есть в `people.phone`). Стратегия: база и так личная (режим `0600`, переписка в открытом виде, `docs/cli/notes-and-search.md:5`); абзац в справочнике.
- Риск: конфликт с потоком `client_restart` в `tgclient/client.go`. Стратегия: одна строка в `chats`, остальная логика в своих файлах.
