## Goal

Агент указывает чат любым из принятых способов и читает его историю и отдельные сообщения: `chat resolve`, `chat info`, `chat invite-info`, `chat list --type`, `message history`, `message get`, `message pinned`. Списки умеют выводиться построчно (JSONL) и листаются курсором между вызовами. Всё только чтение.

## Scope

- В плане:
  - 3.9 ссылка на чат: `@user`, `user`, числовой id (формат Bot API), `-100id`, телефон из контактов;
  - 7.2 `chat resolve`, `chat info`, `chat invite-info` (без вступления), фильтр `chat list --type`;
  - 4.1 `message history` с `--since`, `--until`, `--topic`, `--limit`;
  - 4.2 `message get` по id и `message pinned`;
  - 4.8 курсор: непрозрачная строка, агент передаёт её в следующий вызов;
  - 3.2 вывод списков построчно (JSONL);
  - код выхода для ненайденного чата или сообщения;
  - тесты на подмене Telegram, обновление `AGENTS.md`, `FEATURES.md` (статусы) и справки `just`.
- Вне плана (отдельные планы):
  - поиск (4.3), контекст вокруг сообщения (4.5), комментарии к постам (4.4), непрочитанные сообщения (4.6.2), mark read (4.7);
  - ссылки на сообщения как вход и выход (3.10);
  - локальная база и офлайн-поиск (раздел 10);
  - скачивание и отправка медиа (раздел 6), любые записывающие действия;
  - TOON, `--fields`, самоописание команд (план про контракт).
- Затрагиваются: `internal/{rpc,daemon,tgclient,cli,output,exitcode}`, новый пакет `internal/chatref`, `FEATURES.md`, `AGENTS.md`, `bin/just/`.

## Main invariant

- Код плана не вызывает ни одного метода Telegram, который пишет или меняет данные аккаунта (в том числе пометку прочитанным и вступление в чат).
- Существующие команды (`daemon`, `auth`, `chat list`) и коды выхода 0 до 6 не меняют смысла.
- Ответ любой команды остаётся одной строкой JSON-конверта; исключение только явный `--format jsonl`.
- Текст чужих сообщений приходит агенту как есть, без пометок (решение владельца); Daemon и CLI его не исполняют и не пишут в логи.
- Ответ Daemon не превышает кадр 1 MiB: страница истории обрезается по размеру, а продолжение отдаёт курсор.
- `internal/cli` по-прежнему не импортирует `tgclient`, `store`, gotd (тест границы зелёный).
- `just check` зелёный на каждом шаге.

## Risks and strategy

- Риск: числовой id пользователя или канала, которого сессия не видела, не разрешается (нет access hash). Стратегия: разрешать через `peers.Manager` с хранилищем, заполненным из диалогов; при неудаче отдавать код `not_found` с подсказкой использовать `@username` или `chat list`.
- Риск: страница истории с длинными сообщениями не влезает в кадр 1 MiB. Стратегия: Daemon набирает сообщения, пока закодированный размер не дойдёт до порога, и возвращает курсор на остаток.
- Риск: FLOOD_WAIT на длинной истории. Стратегия: код 6 и время ожидания возвращаются как сейчас; повторов Daemon не делает; курсор позволяет продолжить.
- Риск: чтение истории форумного топика и закреплённых сообщений устроено иначе, чем обычной ленты. Стратегия: Step 1 проверяет это по коду библиотеки, живая проверка в шаге 12.
- Риск: чужой текст содержит инструкции для агента. Решение владельца: ответы с текстом сообщений ничем не помечаются. Правило из `AGENTS.md` (чужое содержимое читается как данные) остаётся правилом для агента.
- Риск: утечка телефона из контактов в логи. Стратегия: Daemon не логирует параметры запросов (уже так, тест на секреты расширяется на ссылку-телефон).
- Решение: разбор ссылки на чат вынесен в пакет `internal/chatref` без зависимостей: это чистая логика с табличными тестами, её переиспользуют `daemon` и будущая локальная база.

## Known facts

- Живая проверка 2026-11-13 нашла и исправила три расхождения: (1) `--until` и `--since` включают сообщение ровно на границе (Telegram отдаёт сообщения до `offset_date` включительно), справка исправлена; (2) в gotd `ResolveDeeplinkJoin` не принимает ссылки `t.me/+хэш` (проверка домена), `invite-info` теперь вызывает `messages.checkChatInvite` напрямую; (3) числовой id пользователя, которого сессия ещё не видела, давал `telegram_error` («got empty result for InputUser»), теперь это `not_found` и срабатывает однократная подгрузка диалогов, после неё такие id разрешаются.
- В сообщение добавлено поле `pinned`: оно показало, что `message pinned` отдаёт именно закреплённые (в проверенном чате их не меньше 100).
- Отрицательный id пишется после `--`, а флаги перед ним: `message history --limit 2 -- -100…`.
- В `zsh` команда `echo` раскрывает `\\` в строке и ломает JSON при разборе в `jq`: в проверках использовать `printf '%s'`.

- Аудит API gotd/td v0.166.0 (2026-11-13), проверено по `go doc` и исходникам:
  - `peers.Manager.Resolve(ctx, from)` принимает `@name`, `name`, `t.me/name`, `tg://resolve?domain=`, `+телефон`; `ResolveTDLibID` принимает id в формате Bot API (он совпадает с нашим); `ResolveUserID`, `ResolveChatID`, `ResolveChannelID`; ошибки `PeerNotFoundError` и `PhoneNotFoundError`; для работы нужен `Options{...}.Build(api)` и `Init`;
  - `Manager.ResolveDeeplinkJoin(ctx, link)` возвращает `tg.ChatInviteClass` без вступления: годится для `invite-info`;
  - у `peers.Channel` есть `ParticipantsCount`, `IsBroadcast`, `IsSupergroup`, `Raw`, `FullRaw`; у `peers.User` есть `FirstName`, `Phone`, `Contact`, `Raw`;
  - история: `query.Messages(api).GetHistory(...)` с `OffsetID`, `OffsetDate`, `BatchSize`, `Iter`; форумный топик: `GetReplies(...).MsgID(topicID)`; закреплённые: `Search(...).Filter(&tg.InputMessagesFilterPinned{})`; сообщение по id с сущностями: `GetMessagesWithEntities`;
  - числовой id, которого сессия ещё не видела, может не разрешиться: менеджер без постоянного хранилища теряет кэш при перезапуске Daemon; обход: однократная подгрузка диалогов при первой неудаче.
- Chat id формата Bot API: пользователи положительные, базовые группы отрицательные, каналы от `-1000000000000` (проверено в `chatref` тестами).

- Первый план выполнен в коде и автотестах (шаги 1-10 и 12), шаг 11 (живой вход) ждёт владельца.
- Daemon уже отдаёт `chat.list` с id в формате Bot API: группы отрицательные, каналы и супергруппы от `-1000000000000`.
- Лимиты протокола: кадр 1 MiB, 16 параллельных запросов, дедлайн запроса 120 секунд.
- Ошибки Telegram приходят как `*rpc.Error`: FLOOD_WAIT (код 6, время ожидания), не вошёл (код 4), прочее (код 5).
- Лимит на один запрос истории: в документации Telegram («A limit on the number of objects to be returned, typically between 1 and 100», core.telegram.org/api/offsets) и в gotd (размер страницы по умолчанию 100, «capped by the server limit»). Числа 200 и 768 KiB в первой версии плана предложил я без источника: 200 это два запроса по 100, 768 KiB это 3/4 кадра 1 MiB, выбранные мной как запас, а не измеренные.
- Как сделано у других (изучено по коду и README, дата 2026-11-13):
  - установленная `tg` 0.5.1: `message history` с `--limit` (по умолчанию 50, минимум 1, максимума нет) и `--offset`; пагинация смещением, курсора нет; `--until` через серверный `offsetDate`, `--since` фильтром на клиенте после получения (история идёт от новых к старым); `--topic` передаётся как `replyTo`; кадр Daemon 1 MiB (`MAX_FRAME_BYTES`), обрезки страницы по размеру нет; в `search` страница запроса `min(100, остаток)`;
  - `kaosb/tgcli` (Go): `msg ls --limit` по умолчанию 20, максимума нет, один запрос `MessagesGetHistory` с этим лимитом без листания; `chat ls` по умолчанию 50;
  - `chigwell/telegram-mcp`: `get_messages(page, page_size=20)` смещением, `list_messages(limit=20)`, у глобального поиска `page_size` от 1 до 100 с комментарием «at most 100 per request»; `get_messages_after(after_id, limit)` возвращает `has_more`, сообщения в порядке от старых к новым, отрицательный `after_id` отклоняется; пагинация по id, а не по смещению;
  - `overpod/mcp-telegram`: курсоры обновлений `{pts, qts, date}` хранит агент;
  - `iyear/tdl` (на gotd): `messages.NewIterator(q, 100)` листает сам, фильтры по времени, id и «последние N», `--topic`, `--reply`.
  Вывод: единого максимума нет, 100 встречается только как размер запроса к Telegram; курсор по id ближе к нашему (у `chigwell` флаг `has_more` и пагинация по id), смещение у `tg` и `chigwell` ломается при появлении новых сообщений между вызовами.
- Худший размер одного сообщения (4096 символов, до 24 KiB в JSON с экранированием) в этом плане предположение: проверяется в Step 1.
- В gotd геттеры необязательных полей (`GetFirstName`, `GetUsername`) возвращают значение только при поднятом флаге: тестовые данные собираются сеттерами.
